# 掌上多模态机器人：硬件选型与端侧推理调研

整理日期：2026-10-09  
项目：Orange Pi Zero 3W 6GB / 掌上机器人  
版本：v1.0，基于项目实测、既有调研对话及用户补充需求整理

> 本文是研发与选型文档。板端实测发生于 2026-10-08，不代表当前在线状态；外部价格和基准沿用历史调研，未在本次整理中重新联网核价。未经核实的数据注明为参考或待复核，不能作为采购报价和性能承诺。原始对话另存为《原始调研摘录.txt》，正文以用户最后确认的“一个统一大脑＋单步动作生成器”为准。

## 1. 需求、边界与当前建议

目标是一台手掌大小、便于携带、有一定电池续航的机器人，具备以下能力：

| 能力 | 具体需求 | 设计约束 |
| --- | --- | --- |
| 视觉 | 拍照、人物/目标检测和跟踪、图片理解 | 大脑接收关键帧；不要求 VLM 持续处理 30 FPS 视频 |
| 声音定位 | 判断说话人方向，并结合视觉找到对应人物 | 同步多通道音频、时间戳和相机/麦阵列坐标标定 |
| 语音接口 | ASR 识别语音、TTS 合成回复、播放时继续监听 | 需要 VAD；同时听说时需要可靠的 AEC 和播放参考信号 |
| 理解与决策 | 一个统一的 VLM/LLM 大脑 | 优先轻量模型；端侧主要考察 3B 及以下，7B 作为扩展对照 |
| 动作生成 | 数百 M 参数、后续改成一次前向生成一段骨骼序列 | 不再以持续多步 diffusion 作为最终方案前提 |
| 动作执行 | 骨骼重定向、IK、轨迹平滑和约束检查 | 电机闭环与独立急停由 MCU/专用控制器承担 |
| 部署与形态 | 初期允许云端，后续逐步迁移到端侧 | 同时考察整机体积、重量、功耗、续航和工程成本 |

已有资产是 Orange Pi Zero 3W 6GB 和 SanDisk 64GB TF 卡。当前优先保留它，用于采集、视觉检测、语音前端、融合和动作接口；统一大脑可以先放局域网电脑或云端。单步动作模型完成后，先验证 A733 NPU 的算子兼容和量化质量，再决定是否升级。

若要求 3B VLM 在机器人本地运行，小型 RK3588S/S2 16GB 板卡或计算模组是重点候选；若自定义模型频繁迭代、CUDA 兼容性比成本和续航更重要，再考虑 Jetson。RK3566 不适合作为已有 A733 的计算性能升级。

## 2. 系统架构：只有一个统一大脑

VLM 通常包含视觉编码器、投影层和语言模型主干。这些组成同一个理解与决策系统，不需要再串联一个独立 LLM 作“第二个大脑”。ASR/TTS 是输入输出接口，DoA/跟踪是实时感知工具，动作模型是执行策略生成器。

```text
同步麦阵列 ─→ AEC / VAD / DoA ───────────────┐
     └─────→ ASR ─→ 语音文本 ──────────────┤
相机 ─→ 检测 / 跟踪 ─→ 关键帧＋人物编号 ────┤
机器人状态 / 历史摘要 ──────────────────────┤
                                           ↓
                              一个统一 VLM/LLM 大脑
                               ├─ 回复文本 → TTS
                               └─ 结构化动作条件
                                           ↓
                               单步动作生成模型
                                           ↓
                        骨骼序列 → 重定向 / IK / 约束检查
                                           ↓
                              MCU / 电机驱动 / 独立急停
```

声音定位优先在阵列 DSP 或机器人本地完成。把压缩单声道传给云端后，原本的通道间时间差和相位关系通常已经丢失；它适合语义理解，不适合替代本地定位链路。

建议大脑输出结构化动作条件，例如：

```json
{
  "action": "turn_and_greet",
  "target_person": 2,
  "target_azimuth_deg": -32,
  "emotion": "friendly",
  "duration_s": 2.5,
  "intensity": 0.6
}
```

动作生成器将其变为 `[T, J, D]` 序列，`T` 是时间帧数，`J` 是关节数，`D` 是所选位置或旋转表示。接口必须约定单位、坐标系、关节顺序、采样率、时间戳和有效期。将上一段动作末尾若干帧作为条件，可以帮助连续片段衔接；仍需验收边界速度和加速度。

## 3. 现有 Zero 3W：已验证的事实

### 3.1 板卡与系统快照

| 项目 | 2026-10-08 项目记录 |
| --- | --- |
| SoC | Allwinner A733，2×Cortex-A76＋6×Cortex-A55 |
| CPU 频率 | 本机大核最高约 2.0GHz，小核约 1.8GHz |
| 内存 | 6GB LPDDR5；Linux 显示约 5.7GiB，空闲快照约 5.5GiB available |
| GPU | PowerVR BXM-4-64；本项目未完成 GPU 通用推理验证 |
| NPU | 单核 VIP9000，标称约 3 TOPS；当前频率 1.008GHz |
| 系统 | Orange Pi Ubuntu 22.04 Jammy Server 镜像 1.0.2 |
| 内核 | `6.6.98-sun60iw2` |
| 系统盘 | SanDisk 64GB TF；根文件系统约 58G，使用 2.7G、可用 55G |
| 温度 | 当时 SoC/NPU 约 63–66°C；环境、外壳和散热条件未标准化 |
| 摄像头/麦克风 | 当时未接入 UVC 摄像头和 USB 麦克风 |

6GB 是运行内存，不能据此判断有没有焊接 eMMC/UFS。默认板载存储选配情况应以实物和订单 SKU 为准。

原系统有 `run-rpc_pipefs.mount`、`dnsmasq.service` 两项失败，分别涉及 NFS/RPC 和 DNS 端口冲突；当时不影响 Wi-Fi 客户端、SSH 和 NPU 示例。此处仅保留诊断记录，不宣称所有应用均不受影响。

### 3.2 TF 卡能力

卡的 SD Status 寄存器报告 A2、U3、V30、Class 10；当前链路为 UHS-I SDR104、4-bit、150MHz。应用等级是 A1/A2，没有 A3。仅凭寄存器不能确定具体零售系列，也不能代替真伪和全盘容量检测。

| 测试 | 结果 | 能说明什么 |
| --- | --- | --- |
| 512MiB 顺序读取 | 约 67.7MB/s | 模型文件加载速度够用 |
| 512MiB 临时文件直接写入 | 约 57.2MB/s | 本次短时顺序写性能正常 |
| 测试后日志 | 未发现 MMC I/O 或 ext4 错误 | 本次访问没有观察到存储异常 |

模型载入内存后，常驻推理通常不再依赖 TF 顺序读取。100MB 文件按上述读速仅计算数据传输约 1.5 秒，完整模型初始化还包括解析、内存分配和运行时准备。

本次没有测随机 IOPS、长时间写入、缓存耗尽后速度及寿命。长期录像、ROS bag 和高频数据库应考虑耐久卡或 SSD；掌上电池方案还需权衡 SSD 的空间、功耗和重量。

### 3.3 NPU 已跑通，但不等于所有模型已适配

已验证 `vipcore` 模块、`/dev/vipcore`、VIPLite 用户态库和预装 `.nb` 模型可协同工作。

| 模型/程序 | 实测结果 | 计时范围 |
| --- | --- | --- |
| 预装 `vpm_run` 小网络，输入 224×224×3 | 返回 0；profile 约 2.7ms | 该示例网络推理；不是 YOLO 或 VLM 的延迟 |
| 预装 YOLOv5 图片示例 | 检出 dog、truck、bicycle | 启动、加载、读图、预处理、推理、后处理、写图合计约 413ms |

413ms 是一次命令行调用的墙钟时间，不能直接作为常驻摄像头吞吐率，也不能把 2.7ms 小网络测试宣传为 YOLO 性能。尚未完成视频连续推理、长时间散热、精度数据集和多模型并发测试。

板上复测命令：

```bash
opi-npu-test status
opi-npu-test smoke 1
mkdir -p ~/npu-output
cd ~/npu-output
opi-npu-test yolo
```

更详细的驱动、用户态和文件校验值保存在项目 `npu/README.md`、`npu/runtime-sha256.txt`；TF 记录在 `docs/storage-check.md`。

## 4. 厂商、SoC 与板卡的关系

Raspberry Pi、Orange Pi、Radxa 等主要提供开发板、计算模组、系统和配套生态，不能简单称为半导体封装厂。Rockchip、Allwinner、Broadcom、NVIDIA、Hailo 则对应不同的处理器或加速器方案。树莓派也有自研芯片/IP，不能一概归为只组装第三方 SoC。

| 维度 | Raspberry Pi | Orange Pi / Radxa 等板卡 |
| --- | --- | --- |
| 优势 | 系统、相机栈、文档、社区与配件的一致性较好 | SoC、内存、接口和价格选择广，RK 系列集成 NPU |
| 需评估 | Pi 5 本体没有 NPU，叠加 AI HAT 增加成本和厚度 | BSP、驱动、转模工具和维护质量因具体型号而异 |
| 选择原则 | 优先完整生态和支持周期时重点考虑 | 优先集成算力、内存容量、接口与成本时重点考虑 |

没有“某品牌所有板子都更好”的结论。应比较具体 SKU、系统版本、模型运行时和实物装配尺寸。

### 4.1 主要芯片比较

| 平台 | CPU | GPU | NPU/AI 路线 | 对本项目的意义 |
| --- | --- | --- | --- | --- |
| A733 | 2×A76＋6×A55 | PowerVR BXM-4-64 | 标称约 3 TOPS，ACUITY/NBG/VIPLite | 已有、可用；视觉检测适合，自定义转模成本较高 |
| RK3566 | 4×A55 | Mali-G52 2EE | 约 1 TOPS INT8，RKNN | 工具链较成熟，但整体计算能力不构成升级 |
| RK3576 | 4×A72＋4×A53 | Mali-G52 系列 | 6 TOPS，RKNN/RKLLM | 较低成本的本地大脑候选 |
| RK3588 系列 | 4×A76＋4×A55 | Mali-G610 MC4 | 6 TOPS INT8，RKNN/RKLLM | 16GB 小型板是本项目主要端侧候选 |
| Pi 5 / BCM2712 | 4×A76，2.4GHz | VideoCore VII | 本体无 NPU；CPU 或外接加速器 | 本体 CPU 较强，但不能据此承诺 3B VLM 速度 |
| Pi 5＋AI HAT+ 2 | 同 Pi 5 | 同 Pi 5 | Hailo-10H，宣传峰值 40 TOPS INT4，独立 8GB | 需确认目标模型有可用编译版本和运行时 |
| Jetson Orin | 按模组配置的 Arm CPU | NVIDIA Ampere CUDA GPU | CUDA/TensorRT 等 | 自定义模型灵活，需承担功耗、散热和价格 |

TOPS 必须同时说明精度、稀疏性、功率模式和支持的算子。不能用 `40÷6` 推算 Hailo 相对 RK3588 的 VLM 速度。

A733 相比树莓派 Zero 2 W 的 4×A53/512MB 是明显升级；相比 Pi 5 不存在全方面领先。RKNN Model Zoo 出现某模型，并不代表 RK3566、RK3576、RK3588 每个平台都支持该模型；需要逐行核对支持列表。RK3566 不应按 RK3588 的 RKLLM 能力规划。

### 4.2 RK3588 后缀说明

| 型号 | 主要差异 | 对模型推理的结论 |
| --- | --- | --- |
| RK3588 | 完整接口版本，更多高速 I/O 资源 | 适合需要更多相机、PCIe 和网络接口的板卡 |
| RK3588S | 精简部分外围接口、封装较小 | 核心 CPU/GPU/NPU 同档，不能因 S 判断推理能力大幅下降 |
| RK3588S2 | S 系列修订，摄像头接口/引脚兼容需查具体资料 | 不把 S2 当作 NPU 算力升级；板级替换应依据应用说明 |
| RK3588J | 面向工业条件的 SKU | 温度、频率和可靠性要求优先；更贵不代表更快 |
| “RK3588S1” | 原始调研未找到可信的标准规格依据 | 采购前核对芯片丝印、板卡版本和厂商数据表 |

历史对话包含封装尺寸、CSI 路数和 J 版本具体时钟，但未附可追溯原始文档。本版不把这些细节作为 PCB 设计依据。对于 VLM，内存带宽、散热、功率限制和运行时版本可能比上述后缀更影响结果。

## 6. 麦阵列、音画融合与定位

普通 USB 麦、双麦、同步原始四麦和带 DSP 的四麦不能混为一类。购买时必须确认：能否输出同步多通道 PCM；如果只输出处理后的单声道，是否另有可读取的 DoA 元数据。

| 方案 | 能力 | 局限 |
| --- | --- | --- |
| 单麦 | ASR、VAD、声音分类 | 单凭一个固定麦克风无法可靠估计常规 DoA |
| 同步双麦 | 基于 TDOA 的方向线索 | 前后/空间歧义受阵列几何影响，不承诺稳定全向定位 |
| 同步四麦 | GCC-PHAT/SRP-PHAT、波束形成实验 | 需要阵列几何、校准、同步与混响处理 |
| 四麦＋DSP | AEC、降噪、波束形成、DoA 等 | 功能、原始通道与角度接口依固件；仍需实装验证 |

相机检测得到人物框和轨迹后，可用相机内参将画面横向位置映射为方向角，再与阵列 DoA 在统一坐标系中匹配。加上时间对齐、置信度、连续性和可选唇动信息，可以减少“把背景说话人配给画面人物”的错误。

DoA 通常给方向，不能自然等同于精确 XYZ。精确距离需要深度/双目、几何多站定位等额外观测。普通单目框尺寸只能在假设下粗估距离。

机器人播放 TTS 时的 AEC 需要与实际播放声音匹配的参考信号；随便加一只不经过参考链路的 USB 音箱，并不自动获得可靠的边说边听。

## 7. 单步动作模型的端侧可行性

用户已经明确：ARDY 在本文中表示自研/改造的数百 M 参数动作生成器，计划改成单步输出动作序列。没有提供唯一仓库或计算图，因此不沿用“某个同名仓库只支持 CUDA/多步扩散”的判断。

### 7.1 权重容量不是运行内存，也不是计算量

以 300M 参数为例，忽略量化元数据的理论权重大小约为：FP16 600MB、INT8 300MB、INT4 150MB。实际还需激活、工作区、输入输出、运行时和与其他模型共享的内存；不能保证只占 1～2GB。

单步减少迭代次数，但单次前向的 FLOPs 仍取决于序列长度、网络宽度、注意力结构及输出形状。不存在“几百 M＋单步＝实时”的直接推论。

### 7.2 建模与部署建议

1. 将统一大脑和动作生成器的接口解耦，动作网络接受固定维度条件及必要历史片段。
2. 先确定输出时长、帧率、关节表示、动作连续性和响应截止时间。
3. 优先固定输入/输出形状，避免不必要的动态循环和自定义 CUDA 算子。
4. MatMul、Conv、归一化和 Attention 也要逐一检查目标编译器的约束，不能仅凭算子名称认定支持。
5. 先建立 FP32/FP16 质量基线，再尝试 PTQ；误差不达标时使用 QAT 或混合精度。
6. 检验关节位置/角度误差、接触/足滑、轨迹平滑、动作边界和约束违规率，不只比较输出张量余弦相似度。
7. 验证单模型后，再测与 ASR、视觉和大脑共享内存、带宽及加速器的排队延迟。

| 平台 | 当前结论 |
| --- | --- |
| A733 6GB | 权重容量有希望；VIPLite/NBG 转换、量化和性能是主要未决项 |
| RK3566 | 工具链可用，但算力更弱；不为此新购替换 A733 |
| RK3576 8GB | 合理候选；不能在模型未导出前承诺实时 |
| RK3588 16GB | 内存余量较好；自定义动作网络仍需 RKNN 适配 |
| Jetson | 通用推理生态灵活；TensorRT 导出也可能需要改图或插件 |

骨骼序列须经过运动学、关节限位、速度/加速度、接触或平衡等检查后执行。断网/超时要进入预先定义的本地状态，不能执行过期目标。具体电机闭环时序取决于执行器和控制器，Linux 主板不替代硬实时闭环。

## 8. 推理速度与上下文：可用证据和空缺

### 8.1 不能只问“3B 每秒多少 token”

比较必须包含：模型名称和版本、总参数统计是否包括视觉塔、量化、图片分辨率/数量、视觉 token 数、提示词长度、上下文、缓存状态、后端版本、功率模式和温度。

VLM 交互总延迟由采集、图像处理/编码、prompt prefill、首 token 和 decode 等阶段构成。若 TTFT 已包含编码和 prefill，就不要再加一次。

```text
热启动一次回复耗时 ≈ TTFT + (输出 token 数 − 1) / decode tokens/s
```

云端路线还需计入上传、网络、排队和流式播放；端侧路线还需计入多模型调度。吞吐率不能替代“用户开口到机器人开始回应”的测量。

## 9. Pi 5 8GB＋AI HAT+ 2 与 Orange Pi 5 Pro 16GB

现有证据不能认定前者对所有 VLM 都更快。HAT+ 2 的 40 TOPS 是特定精度口径，最终速度还依赖图像编码、prefill、decode、内存带宽、数据搬运和编译优化。

## 10. 模型驻留、并发与调度

“TF 能装几十个模型”“内存能同时放几个模型”和“多个模型能同时低延迟推理”是三个问题。不要用模型数量作统一容量指标。

原始调研的候选栈：

| 模块 | 历史内存估算 | 说明 |
| --- | --- | --- |
| SmolVLM-500M Q8 | 约 1.2GB | 社区报告口径，待本板复现 |
| YOLO-nano 级 | 约 100–300MB | 工程估算，随输入/后端变化 |
| 小型 ASR | 约 200–600MB | 模型未定，不能保证 |
| 轻量 TTS | 约 200–500MB | 声学模型、声码器、缓存不同 |
| 300M INT8 动作模型 | 原估约 500MB–1GB | 尚无计算图，作为占位预算 |
| VAD/DoA | 原估约 20–100MB | DSP/CPU、窗口和通道数不同 |

以上估算合计约 2.22–3.70GB，但未含全部系统占用、KV cache、峰值工作区、共享库计量误差和临时复制，因此不能由此承诺“6GB 可同时满载整套模型”。

建议模型常驻以避免重复从 TF 加载，感知持续轻量运行，VLM 按事件读取关键帧，动作按片段生成，ASR/TTS 结合 VAD 和对话状态启停。A733 的共享 NPU 由服务统一排队，并优先满足动作/语音的截止时间；RK 的多核 NPU 也不代表多个模型天然无竞争。

## 11. 掌上机器人：功耗、电池、重量和散热

### 11.1 先定义整机预算

选型前仍需确定：外壳最大长宽高、含电池总质量、单次续航、平均/峰值电机负载、是否有持续 Wi-Fi、是否要求离线大脑。当前尚没有这些硬约束，不能给某块板承诺具体续航。

整机功耗包括计算板、相机、阵列/DSP、Wi-Fi、扬声器、MCU、电机及供电损耗。芯片的 TDP/功率模式不是电池端实测功耗，电机和扬声器的峰值电流也不能用平均值代替。

### 11.2 续航计算示例

```text
电池标称能量 Wh = 标称电压 V × 容量 Ah
预计续航 h ≈ 标称能量 Wh × 综合可用系数 / 系统平均负载 W
```

假设 3.7V、5000mAh 电池，标称 18.5Wh；综合考虑可用容量和转换损耗，演算取 85%，负载端可用约 15.7Wh。以下是算例，不对应任何板卡的实测：

| 负载端平均功耗 | 理论估算续航 |
| --- | --- |
| 5W | 约 3.1 小时 |
| 10W | 约 1.6 小时 |
| 15W | 约 1.0 小时 |
| 25W | 约 0.63 小时 |

例如目标 10W 平均负载持续 2 小时、可用系数 85%，需要约 `10×2/0.85 = 23.5Wh` 标称电池能量，约等于 3.7V 下 6.36Ah。相同 Wh 的电池重量也随封装、放电能力和保护电路变化，不能单凭 mAh 指定整机重量。

移动电源标称容量通常基于电芯电压，不能直接乘 USB 输出 5V。还需确认额定输出、峰值电流、快充协商、电量低时的降额和边充边用能力。计算供电与电机供电应按电气设计隔离/分配，避免电机启动导致主板掉电。

### 11.3 体积与续航下的取舍

- 最省空间和预算：现有 A733＋远端统一大脑，本地保留轻量感知、动作接口和 MCU。网络传输功耗、延迟和断网策略仍需测。
- 必须本地 1B–3B：优先评估 RK3588S/S2 16GB 小板或模组，按任务触发推理，并实际测电池端能耗。
- Pi＋HAT：不能假设 NPU 峰值更高就更省电，需测完整管线的焦耳/次回复；叠层高度要计入外壳。
- Jetson：开发灵活性较好，但载板、散热、电源与电池可能主导整机重量。适合先作研发基线，再决定产品是否采用。
- 7B：不作为当前掌上续航方案默认目标；先证明 0.5B–3B 在任务准确率上不够，再扩大模型。

## 12. 软件与 NPU 适配路线

### 12.1 A733

当前原厂内核模块与用户态库已通过示例兼容验证，不能因为软件尾版本不同就直接覆盖运行库。

典型流程：固定形状 ONNX → ACUITY 量化/编译 → A733 NBG/`.nb` → VIPLite → 板端质量与性能验证。既有调研记录的目标是 `VIP9000NANODI_PLUS_PID0X1000003B`；当前开发文档指向 `ubuntu-npu:v2.0.10.2`，实际开始转换时须重新核对 SDK、运行时和模型版本。

社区 `a733_npu_driver` 已作为参考克隆，检查时提交为 `aae9287f6d0de4af2f3e253343c58a78e2f3d04f`。其中部分路径、模块名和转换容器版本不适用于本机，不能整仓照搬。其小 LLM/VLM 实验也不证明任意 3B 大脑可在 A733 NPU 上部署。

### 12.2 Rockchip

常规视觉/声学/动作网络走 RKNN；被支持的语言/多模态架构走 RKLLM。既要检查模型支持，也要检查平台支持、量化方式、转换机环境、板端 runtime 和内核驱动。

### 12.3 Hailo 与 Jetson

Hailo 首先确认目标模型、编译产物、上下文和精度；没有相应软件证据之前，不按峰值 TOPS 采购。Jetson 可先用通用框架建立质量/延迟基线，再尝试 TensorRT 等优化；插件、图拆分和版本兼容仍需开发。

## 13. 分阶段实施与验收

| 阶段 | 工作 | 完成标准/状态 |
| --- | --- | --- |
| G0 板端基线 | 系统、TF、NPU 示例 | 已完成初测；未做持续负载验收 |
| G1 传感器 | 接入 UVC 与同步麦阵列，记录时间戳，确认 AEC 参考 | 待采购/接入；可复现采集和已知角度测量 |
| G2 统一大脑接口 | 关键帧、文本、方位/人物 ID 发给同一个远端或本地模型 | 可返回结构化意图，测首响应、完整延迟和失败处理 |
| G3 动作网络 | 固定形状导出、量化、端侧部署 | 与基线比较质量、P50/P95 延迟、峰值内存和能耗 |
| G4 全链路调度 | 视觉、语音、大脑、动作混合负载 | 无失控排队/OOM，满足明确的交互和动作截止时间 |
| G5 便携形态 | 电池、散热、外壳、重量与断网测试 | 在目标外壳与电量条件下达到用户定义的续航 |

建议统一的性能记录字段：硬件/SKU、系统/SDK commit、模型 hash、精度、输入形状、上下文、图像 token、冷热启动、TTFT、prefill/decode 速度、完整 50-token 响应、RSS/加速器峰值内存、平均/峰值输入功率、温度/频率、任务准确率。

语音补记 ASR 的实时率（处理秒数/音频秒数）、识别错误率和 TTS 首包时间；定位补记不同角度/距离/混响下的误差；动作补记片段连续性、约束违规和目标完成率。测试应在目标外壳和供电条件下进行，不只测开盖空载。

## 14. 当前决策与未决问题

1. 保留现有 A733 和 TF 卡，暂不因“RKNN 更成熟”而换成 RK3566。
2. 前期优先投入相机、可靠麦阵列与音频回声链路，统一大脑允许远端。
3. 单步动作生成模型先完成计算图与质量基线，端侧是目标而非现成事实。
4. 本地 3B 主脑重点评估小型 RK3588 系 16GB；Pi＋HAT+ 2 须拿到具体目标模型数据后再比较。
5. 自定义模型开发效率不足时，考虑 Jetson 研发平台，同时单独评估产品电池与外形成本。

尚需补齐的信息：

- 手掌尺寸的具体长宽高、整机质量上限、目标续航和电机负载。
- 统一大脑选用哪个模型、语言要求、视觉任务和可接受首响应时间。
- 单步动作网络的仓库/ONNX、FLOPs、形状、输出片段长度和误差标准。
- HAT+ 2 实际支持的精度组合、目标 VLM 编译包与上下文。
- 所有板卡当前 SKU、含税价格、库存、完整散热/电源/存储 BOM。
- 500M/1B/3B/7B 的统一实测矩阵；目前资料有缺口，不填造出的 token/s。
