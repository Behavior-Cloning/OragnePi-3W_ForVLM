# 语音小模型提速与整段/流式链路评估

日期：2026-10-18。板卡：Orange Pi 3W（RK3588，8 核）；运行时 sherpa-onnx 1.13.8 / ONNX Runtime ARM64。正式代码、权重和结果位于 `F:/Files/OPi-Lab/`。公开语料/官方模型样例，不包含家庭录音。本报告把此前已完成的板端实测、这次新增 KWS 烟囱测试和仍待完成的严格成对延迟验收分开，避免把仿真回放或代理端点说成真实用户体验。

## 结论先行

- **可以提速，但首先应从模型与调度入手。** 同一板端已验证 Silero VAD、GTCRN、多个 ASR 和新增 KWS 能在 CPU 上运行。短小 Paraformer 是当前普通话离线候选中的速度/精度折中点：此前 33 条 AISHELL 派生语料 clean CER 3.98%，平均约 0.71 秒一条（单条约 4.95 秒），明显快于 SenseVoice；流式 Zipformer 的首 partial 更早，但当前模型 clean CER 8.81%，噪声下退化明显，尚不能为低延迟牺牲准确率直接推荐。
- **实时前端可以跟上 16 ms 音频帧。** 75 秒 file-paced 模拟采集里，GTCRN+Silero 前端 p50/p95 每帧处理 11.28/13.23 ms，9/4688 帧超过 16 ms；ASR/Speaker 队列无丢段。它是文件回放模拟，不是麦克风端到端测量。
- **“说完到首字/末字”目前还没有可靠的人声真终点成对统计。** 现有流式探针以音频文件结束/模型自己的端点作参照，无法当作用户说完时间。要严谨报告该指标，必须对同一条音频冻结人工真终点，或明确以独立 VAD proxy 做主统计；此前TODO已把这一项列为未完成。本报告不会伪造该数值。
- **KWS 已完成板端部署运行测试，但未完成唤醒词准确率验收。** 官方随包样例没有可直接核对的中文逐条转写；固定关键词子集在若干中文文件中出现触发，也在被临时标为非目标的样本里触发。由于标签未核验，这不能作为误报率或召回率。定制唤醒词“小机器人”也没有校准。

## 整段与流式架构的时间拆分

**整段/端点后离线 ASR：** VAD等待静音端点 + 将已收集片段送给Paraformer + 返回整句文本。Paraformer在当前短句集单句计算约0.71秒；把它作为“端点发生后的计算时间”是合理的工程估算，但本轮未针对独立真终点做统一的端到端重测。首字和整句最终文本通常同一时刻产生。

**边听边处理：** GTCRN以16 ms帧处理、VAD以32 ms窗口检测；流式Zipformer每80 ms接收一次数据，可在说话时输出partial。旧探针观察到片段开始后约1.6–1.7秒出现第一版文本；这是片段开始坐标，未减去冻结的话音终点，也可能早于说完。模型稳定文本和自然endpoint/final必须另外记时；旧模型的0.5秒静音endpoint曾在日期短语中途截断，“早结束”属于失败而不是低延迟成功。

**建议的当前组合：** 常开小型VAD；噪声明显才启用GTCRN；将当前流式Zipformer作为可选partial预览，保留Paraformer作为 endpoint 后高质量final。产品可先显示“识别中”或partial，最终提交仍等VAD endpoint和Paraformer；这个双通路增加资源，且还没有在新配置上与 NPU LLM 一起完成本轮真实端到端配对验收。若界面不需要边说边显示，直接VAD+Paraformer预计更简单、更稳。

## 如何进一步提速

1. **保持小模型常驻、预热一次。** 模型冷加载与每句推理分开测；此前Paraformer加载约数秒级，不能每句重建模型。
2. **按负载分配核而非盲目加线程。** 已有测试多为单线程单核；当前 realtime 前端CPU帧预算余量不大。新增KWS暂用2个A55核的亲和集合但单线程。尚未做同模型A55/A76、1/2线程的配对矩阵，所以不能声称某核或多线程已获确定加速。小ASR曾在CPU6/7跑通，但与LLM复用大核可能争CPU；须比较LLM独占和混跑。
3. **只对噪声启用降噪。** GTCRN的0.58 RTF意味着可以实时，但持续耗用一个CPU核。低噪环境可测直通路径；打开降噪可能改变ASR准确率，不能仅凭SI-SDR改善就认定中文识别变好。
4. **流式粒度和端点必须一起调。** chunk太小提升调度次数，太大增加首字时间；提高端点静音阈值能降低截句但增加说完等待。旧流式Zipformer对0.5秒端点有截句案例，需与整段Paraformer配对测日期、数字、否定词和人名。
5. **KWS和VAD职责分开。** KWS做关键词检测，VAD负责话段边界；静音及普通语音做负样例，命中后保留前滚音频以免切掉命令首字。阈值要按家庭麦克风/噪声和重复唤醒率校准。
6. **持续记录CPU频率、温度和LLM并发。** 之前GTCRN+VAD链在NPU模型并行期间可保持帧实时性，LLM约15.5 tokens/s；但这不能替代本报告建议的新Paraformer/流式Zipformer/ KWS组合对LLM TTFT和decode速度的配对测试。

## 新增：VAD静音停止后的端到端延迟与提速实测（2026-10-18）

按用户指定的停止规则，使用 Silero VAD 连续检测静音 500 ms 后结束当前话段；因此这组指标就是“系统按VAD判断用户说完→识别文本返回”的代理端到端时间。6条公开 AISHELL 普通话音频按真实时间节拍回放，并在末尾追加800 ms静音，板端 CPU2–3、单线程、GTCRN前端开启。每条共享同一个独立VAD标出的语段末代理时间；该点不是人工音素标注，也不等于说话人声学上的最后一个发音样点。

| 事件 | 中位数 | 含义 |
|---|---:|---|
| VAD语段末代理点→VAD静音端点回调 | 0.60 s | 主要是500 ms静音阈值及帧调度；该值直接体现“静音后停止”的等待 |
| VAD代理点→Paraformer完整结果 | 1.12 s | Paraformer同一时刻输出首字和完整末字；端点后ASR计算约0.52 s（分段中位数约值） |
| VAD代理点→流式Zipformer首个非空partial | −3.16 s | 说话过程中已出现可读文本，属于可修改草稿，不是用户说完后的延迟 |
| VAD代理点→流式Zipformer flush final | 1.18 s | 完整结果等待；强制flush最终稿，不等同自然endpoint的可靠final |

Paraformer最终 CER 为2.08%（96个参考字符、5/6句完全匹配）；Zipformer final CER 为8.33%（6句中3句完全匹配）。在日期句，VAD把一句话切成两个话段，流式文本出现“中心网…电锯…”，并未正确还原原文。流式可在说话过程中给草稿，但当前准确率不足以取代Paraformer作为提交文本。该回放模拟并无麦克风采集、AEC或家庭环境录音；端点定义遵循VAD静音停止，不能据此宣称人工冻结的真实生理/音素终点。

### 提速配置的板端配对结果

同6句、模型预热后分别测 A55（CPU2–3）与 A76（CPU6–7），1/2线程。Paraformer单句热推理中位数：A55单线程0.726 s、双线程0.474 s；A76单线程0.204 s、双线程0.145 s。A76双线程较A55单线程约快5.0倍，但它占用LLM共用的大核，是否用于实时语音要以混跑体验为准。该矩阵中Paraformer单线程CER 2.08%（5/6句完全匹配）；线程配置改变后速度有收益，但小样本没有证明所有线程设置的识别质量等价。模型冷加载单独测量：Paraformer约6.51 s，因此必须常驻并预热，不能按每句话重复加载。

前端热推理p50：Silero VAD约0.277 s/5.0 s音频（RTF 0.054），GTCRN约2.81 s/5.0 s（RTF 0.555）。同一实时链路前端帧p95约9.5 ms，小于16 ms帧周期，6条音频均无超帧。GTCRN开关对合成噪声小样本的准确率没有稳定改善：10 dB子集两种条件都4.69% CER；0 dB子集未降噪21.88%，降噪25.00%。因此清洁音频先走直通更省CPU；有噪环境是否启用需按设备实测。

LLM并发探针在A55上运行Paraformer CPU2 +“小白小白”KWS CPU3，同时在NPU跑LLM（CPU6–7），D64和D256各一轮。D64解码15.533→15.493 token/s、TTFT 1.252→1.245 s；D256解码15.545→15.438 token/s、TTFT 4.974→4.977 s。单次测试变化很小，不足以证明统计显著；两次结束后NPU driver占用均回到0。KWS正例合成音4/4触发、公开普通语音负例0/24触发，但真人音色与家庭误唤醒率尚未验收。

### 当前建议

先让VAD在500 ms静音后封口并立即运行常驻的Paraformer；公开回放数据显示从VAD判断结束到完整文本约0.52 s，从共享VAD话音末代理到完整文本约1.12 s。说话期间可并行显示Zipformer草稿，但最终用Paraformer覆盖，避免流式模型日期/人名错误直接提交。若更看重延迟，可在CPU6–7双线程跑ASR，约0.145 s/短句；但它与NPU LLM调度共享大核，现有D64/D256单轮混跑只覆盖LLM测速，没有覆盖用户说话时LLM持续解码造成的ASR p95等待。部署建议优先A55双线程或A76单线程做新一轮高并发压力验证，再据端到端p95选择。

延迟表格中流式“首字”定义为首个非空partial，可能回改；没有把事后稳定文本追溯时间冒充在线稳定首字。若需要严格“人确实说完”的语音学终点，下一轮应对音频逐条听标并冻结时间戳，再和同样的VAD端点并列统计；本次已按用户提出的VAD静音停止规则给出系统可用的端点后指标。

## 新增：连续对话完整链路实测（2026-10-18）

本轮按连续三轮对话回放执行：`小白小白` KWS → 16 ms 前端帧 → Silero VAD（500 ms静音封口）→ Paraformer → 常驻 LLM。每轮把上一轮用户文本和回答放入下一轮上下文。唤醒词使用公开 Microsoft Huihui 中文 TTS 合成正例，命令使用公开 AISHELL 音频；不是家庭麦克风录音。为避免把尾部补静音算进ASR，VAD检测到首个完整话段即封口并提交。

| 方案 | 降噪/ASR | VAD端点→ASR完成 p50 | 唤醒→首token p50 | 唤醒→完整回复 p50 | ASR完全匹配 |
|---|---|---:|---:|---:|---:|
| full | GTCRN开启，A55 CPU2–3，1线程 | 0.625 s | 8.396 s | 8.688 s | 2/3 |
| fast | GTCRN关闭，A76 CPU6–7，2线程 | **0.213 s** | **7.189 s** | **7.679 s** | 2/3 |

KWS触发延迟约1.46–1.50 s（由合成唤醒词音频长度决定）；命令从开始播放到VAD端点中位数约5.26 s（full）和4.98 s（fast），主要是命令本身的语音时长加500 ms静音判定，不是模型计算等待。前端帧 p95 为full 10.47 ms、fast约0.008 ms；两者均无超过16 ms的帧。fast相对full的端点后ASR节省约0.41 s，端到首token节省约1.21 s，完整回复节省约1.01 s。

full轮次温度约49.8–50.7°C，fast约48.2–50.5°C；每轮可用内存约4.19–4.20 GiB。常驻 CPU llama-server 的 RSS约1.10 GiB，采样到的系统 loadavg 约0.3–0.7（1分钟字段）；没有交换空间压力。当前对话服务是板上 CPU Qwen2.5-1.5B Q4 llama-server，**不是 NPU LLM**。现有NPU full_model探针只接受固定 token fixture，不能把它冒充成“ASR文本驱动的NPU连续对话”。

### 方案结论

在当前公开语音回放和已有模型组合下，优先采用 `fast`：安静环境关闭GTCRN，Paraformer使用A76双线程，VAD仍保持500 ms封口；它把端点后ASR压到约0.21 s，完整链路中位数约7.68 s。噪声检测或家庭环境实测恶化时再切换GTCRN，但full会增加约1秒端到端等待。两套方案ASR样本均为2/3完全匹配，不能据三条样本判定精度等价；“王思聪将朱圣祎…”仍出现“朱胜伟”，需保留文本纠错/确认策略。
