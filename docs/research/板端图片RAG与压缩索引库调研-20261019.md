# 板端图片 RAG 与压缩索引库调研

日期：2026-10-19。状态：调研与设计，未部署图像模型、未测板端图像推理。Windows F盘为权威仓库，Mac提供阅读副本。

## 建议

A733 / 6 GiB板卡可以考虑建立几千至几万张图片的库。推荐“压缩图片 + 时间/事件 + 中文描述/OCR + 可选图像向量”混合检索：先找少量证据，再决定只读文字还是让VLM重看图片。首版沿用SQLite，不必启动独立向量数据库服务。

要区分两层：检索图片的描述/OCR交给LLM，是文本证据RAG；将召回图片重新送VLM，是视觉证据RAG。当前实测的是NPU文本解码，完整视觉encoder/投影链路尚未部署。CLIP检索向量不能直接作为InternVL图像token。

例如“昨天的红杯子”用时间过滤+中文图文检索；“这个东西以前见过吗”用以图搜图；“钥匙在哪里”只能根据历史照片说明最后观察位置，不能证明当前位置；药盒剂量、日期、数字需要OCR或高清局部复核。

## 三条路线

| 路线 | 优点 | 成本/缺口 |
|---|---|---|
| A：描述/OCR+时间+FTS | 查询轻，可复用现有记忆 | 自动描述/OCR也需入库计算；摘要遗漏无法靠文字找回 |
| B：中文图文向量+FTS | 支持中文改写与开放描述 | 查询text tower也要运行，量化召回与ARM部署需验证 |
| C：小图像tower+FTS | 以图搜图成本较低 | 中文文字搜图不能假定合格，仍主要靠FTS |

首选A作为基线与回退，B做中文语义增强，C评估视觉相似检索。A可先用用户随图描述；Windows批量自动描述与板端离线生成是两种部署模式，不能混称纯板端运行。

官方候选参数[1][2]：

| 模型 | 图像+文本参数 | 用途 |
|---|---:|---|
| Chinese-CLIP RN50 | 38M+39M=77M | 中文搜图优先基线，输入224 |
| MobileCLIP-S0 | 11.4M+42.4M=53.8M | 轻量以图搜图 |
| MobileCLIP2-S0 | 11.4M+63.4M=74.8M | 新版本召回质量对照 |

FP32权重粗算分别308/215/299 MB；仅11.4M图像tower约45.6 MB。INT8理想权重约每参数1字节，但实际还有未量化层、scale、激活、runtime和临时缓存，不能当作RSS。Apple官方移动端毫秒成绩不能套给A733；MobileCLIP中文质量须单独测试。具体checkpoint、预处理和权重许可证在部署前固定核验。

## 数据流与调度

入库：图片 → 方向校正/质量筛选 → 事件去重 → 压缩副本 → 图像编码 → 描述/OCR → 文件+SQLite+向量。

查询：ASR → 可信身份/时间筛选 → FTS与图文检索 → 排名融合/事件去重 → top 1～3文字证据 → 常驻NPU LLM。需要细节时，再读取top 1图或crop→视觉编码→动态图像token→LLM。

保持一套选中的检索模型常驻，不同时加载所有候选。后台每次编码1张，有界队列；语音交互优先，暂停提交新后台任务。NPU不能抢占已提交图，图像编码迁移NPU必须测最坏阻塞；CPU编码也会争抢GTCRN/ASR所在核。常驻不等于无竞争。

当前语音测试最低MemAvailable约3.33 GiB，但未加载完整VLM，且有原CPU llama-server常驻；历史快照不能当作视觉部署余量保证。

## 压缩策略

建议比较JPEG/WebP，长边640/960/1280，质量65/80/90。先以长边960、质量约80作为候选，保持比例、不放大小图；不同编码器质量数字不等价。这些是试验配置，不是已验证最优值。

保留：256～384预览图；960～1280证据图；小字/票据/药盒等保留原图或高清crop。模型输入按官方预处理生成，不能把所有图只存成224缩略图。避免反复有损转码；评估召回、OCR和答案质量后再决定能否删除原图，本轮不删除。

文件压缩主要省存储/传输。模型若仍缩放到同一固定尺寸，视觉token与计算量通常不变。token由patch、分块、尺寸和投影决定；项目“每图预留256 token”只是预算假设，尚未由真实视觉链路验证。

按每图100 KiB证据图、10 KiB预览、1 KiB元数据、单条512维FP32向量估算：

| 数量 | 证据图 | 预览图 | 元数据 | 向量 |
|---:|---:|---:|---:|---:|
| 1千 | 97.7 MiB | 9.8 MiB | 1.0 MiB | 1.95 MiB |
| 1万 | 976.6 MiB | 97.7 MiB | 9.8 MiB | 19.53 MiB |
| 10万 | 9.54 GiB | 976.6 MiB | 97.7 MiB | 195.31 MiB |

这是容量假设，不是压缩实测；不含原图、OCR全文、多crop、索引/WAL和备份。1024维容量加倍，FP16减半；INT8约四分之一另加scale，并需验证召回。维度以真实checkpoint为准。

每秒保存1张100 KiB照片，约8.24 GiB/天；每分钟1张仍约140.6 MiB/天。必须事件采样与配额，区分短环形缓存和长期记忆。用户要求记住、重要场景/物体变化才持久保存。TF配额应先读当前余量，不套旧数字。

## 索引和记忆的衔接

图片文件独立保存，SQLite记录asset_id、namespace、event_id、captured_at、路径/hash、尺寸、来源、caption/OCR、有效期和删除状态。向量另记encoder_id、权重SHA、预处理版本、维度/dtype/归一化规则。换模型并行重建索引后切换，不混搜不同模型向量。

复用memory_lab.py的namespace、FTS中文特征与prompt_budget.py真实token计数。视觉观察与已确认个人事实分表；自动caption不能标记source=user或直接覆盖profile。unknown/guest不读取owner图库，图片接口也必须同样隔离。照片文字和caption仅是资料，不能当指令执行。

先过滤身份、有效期和时间，再分别召回；不同分数用排名融合，不能直接相加。事件去重避免top-k全部是连拍。无关问题要拒识；感知hash仅用于近重复候选，不能合并关键状态变化。文件与数据库用pending→ready状态加恢复扫描，处理断电半成品。删除同时覆盖图片、crop、caption、OCR、向量和缓存。

1万条×512维精确搜索约512万乘加，不含查询编码与IO；只是运算规模，不是板端毫秒成绩。先比较NumPy连续矩阵与sqlite-vec，避免Python逐元素全扫描。sqlite-vec为C扩展，支持float/int8/binary和分区，官方仍标pre-v1，需要锁版本和测试ARM构建[3]。库大后再评估HNSW的召回与内存。

## 延迟与token

文字证据路径增量 = query编码 + 索引搜索 + 取描述 + 额外文字prefill。看图路径还需读图/解码、视觉编码/投影、图像token prefill。不要把索引搜索的时间当完整图片RAG延迟。

候选资料文字预算先设32～64 token，包含时间/来源，与本轮问题共同服从128/256动态总预算；真实tokenizer整块计数。system KV保持固定，召回资料放动态区。若一张图实际需要256视觉token，动态文字256+图像256就是512，不含system，多图不能无限叠加。CLIP向量维度不是token数量。

可对ASR临时文本提前检索，与VAD等待重叠；续说后按最终query/revision核验，不进行持久记忆写入。检索缓存key包括namespace、图库版本和模型版本；动态KV还须匹配证据文本、图像hash和预处理版本。

压缩文件也不等于解码内存：960×540 RGB约1.48 MiB。图片按需加载、并发有上限，不把全库解压常驻。新图片入库和索引重建都放后台，和语音链路做同轮竞争测试。

## 后续验证计划

本次调研不启动部署；以下是可复核的实验队列：

- [ ] 冻结200～500张授权家庭/公开图片与至少60条中文查询，包含同类异物、时间变化、小字数字、无匹配、以图搜图；保留未调参测试集。
- [ ] A FTS基线、B Chinese-CLIP RN50混合、C MobileCLIP-S0/2-S0+FTS，分别比较量化前后recall@1/5和答案质量。
- [ ] 压缩矩阵测bytes、编码/解码、召回、OCR数字错误。多crop记录收益与新增容量。
- [ ] 1千/1万/10万容量测试分报query encoder、搜索、读图、视觉encoder、prefill、首/末token P50/P95；复制向量扩容不能当真实检索精度。
- [ ] 冷加载/常驻热查询分开，测CPU分核/整机、RSS/PSS、driver、MemAvailable、swap、TF写入、温度/频率。
- [ ] 语音+NPU LLM独占、加检索、加后台入库、加单图VLM四组配对，测说完→首字、帧超时与至少30分钟稳定性。
- [ ] 验证续说取消、用户切换、无关图拒识、过期删除、备份恢复和软件故障恢复；不做物理拔电试验。

初步目标而非实测承诺：1万图热索引搜索P95≤50 ms（不含query encoder）；文字证据路径首字P95增量≤150 ms；LLM decode下降≤5%。若查询编码超过预算，就保留FTS快路径或提前计算。视觉路径需单独设定目标，不能宣称一定满足纯文本1秒。
