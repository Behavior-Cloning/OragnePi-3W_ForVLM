# 短前缀、动态输入 NPU 实测

日期：2026-10-18。板端实际运行的是完整 InternVL3-1B 语言模型：24层 decoder、12个两层融合图、12个 prefill 图和4个词表 head，全部走 A733 NPU。runner 与旧15.5 tok/s版本相同，使用 w8-fused2-c1280-cap1-headmse、prefill16、decoder group12、fast greedy、group head，CPU6,7。每个工况1次预热、3次测量，测量顺序交替；输出固定128 token feedback，仅用于稳定测量负载，不是自由回答质量验收。

## 如何理解

持续解码约15.49–15.56 tok/s，和旧峰值15.582 tok/s基本相同；动态输入主要改变首字延迟和总响应时间。D64比D128少约1.23秒，D256比D128多约2.50秒，D384/D512按每128 token约2.5秒近似增长。P64和P128的decode几乎没有区别，说明当前capacity=1280的固定图计算让短前缀主要节省prefill而不是改变逐token decoder速度。

TTFT 是从本次响应计时起点到第一个输出token；preparation_seconds 是到缓存前缀位置的准备时间。旧对照的长前缀准备约20秒，但它的响应TTFT只有约0.63秒，因为计时协议在准备完成后才开始响应计时。短前缀的P64/P128也采用同一“本进程先准备KV、到cached_prefix后重置响应计时”的协议，便于比较增量；这不是跨请求常驻KV服务的真实缓存命中时间。

图片等效行把256 token的视觉占位作为输入长度加入，实际仍喂文本token，没有运行vision encoder、projector，也没有端到端图片采集/预处理，因此不能称为图片推理实测。真实图片还要单独测视觉模块、内存、传输和图接入。

## 产品取舍

- 纯文本日常对话优先D128：相对D64多约1.23秒TTFT，可容纳更多历史，decode保持同一水平。
- 需要更长记忆/历史时D256，TTFT约4.96–4.97秒；应减少无关记忆，而不是默认把所有历史塞进来。
- D64适合短指令或严格响应场景；真实记忆模块必须把记忆正文和包装计入D64，可能挤掉完整历史轮次。
- P64与P128的解码收益很小；P128适合系统规则确实需要更多token的场景，P64可降低准备成本。
- 结果不是问答质量验收。固定feedback保证了同负载计时；仍需在最终prompt格式和真实视觉输入上做少量质量/端到端测试。
