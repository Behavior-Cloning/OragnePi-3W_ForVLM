# Zero 3W 完整模型正确性与加速验收

2026-10-12，按用户补充的研发目标更新。目标不是当前已实现的结论。

在 A733 / 6GB 上，SmolVLM-500M 和 InternVL3-1B 的完整语言生成链路分别达到可接受精度，并在预先公开的 CPU 搜索范围内，超过各场景对应量化档位最快的合格 CPU 实现。按用户最新澄清，本轮两模型主要比较 Q8；CPU GGUF Q8_0 与 NPU per-channel/DFP W8 的编码不完全相同，激活、KV 与敏感 FP16 例外均需披露，通过共同质量门槛后才能比较。不能通过限制 CPU 线程、选择 FP32 慢基线、只测两层或平均两个模型成绩宣布成功。500M、1B 是 VLM 型号，不等于本轮参与推理的语言部分参数量。

## 2026-10-13 精确对齐矩阵（优先于下方旧场景）

用户进一步要求温度也作为场景：**低温40–50°C、中温55–低于65°C、高温65–80°C**，按历史KV准备完、增量响应开始时的实测温度严格入档；共36个模型/历史/新增/温档场景，每格CPU/NPU各预热一次、正式五次。原高温70–80°C停止预热后温度陡降、两次无法入档，在尚无合格高温成绩时调整为65–80°C，失败日志保留，已告知用户。用等待自然散热或独立短暂CPU预热进入温区，预热进程在正式计时前终止并等待退出，不修改频率上限/温控保护。预热/散热耗时独立记录，KV不重建。推理中允许自然升降温，另报响应内温度范围/峰值、频率；这测的是起始温度影响，不是恒温箱下稳态性能。温区达不到则保留失败/缺测，不能换标签。以`thermal-aligned-20261013`为当前主矩阵，之前未分温档r2仅留作过渡记录。

用户要求两模型均为**完整深度**，已缓存历史精确512/1024 token，新增输入32/64/128 token，共12个模型场景；每格CPU与NPU都重新测量。500M全部32层、1B全部24层，包含最终归一化、完整词表输出头和采样；少量层探针仅定位瓶颈，不进入正式结果。

`aligned_fixtures.py`使用各自官方GGUF模板构造完整多轮中文对话，在完整assistant历史轮次后冻结缓存边界。每个模型/历史档的三种新增输入共享完全相同的历史token。新增计数包含用户role、消息终止和assistant生成标记，不能把正文字符数或未计模板的32 token称作新增32。CPU llama.cpp独立复核分词。跨模型因分词器不同，仅长度/任务类型匹配，文本不强求逐字相同；同一模型CPU/NPU输入二进制严格相同。

容量统一为历史+256，即768/1280；最大场景需要历史+128新增+127回灌=767/1279位置。CPU先冻结128步greedy轨迹，忽略EOS以对齐工作量；NPU每步仍计算完整logits与预测，但回灌同一CPU轨迹。每格先检查完整数值门槛，再诊断复现完整logits、预热一次、测量五次。固定轨迹不当作自由对话质量结论。

CPU使用此前线程/绑核筛选的两A76、2线程Q8_0配置重新测量，不称为所有长历史配置已穷举。NPU候选采用32-token批量prefill，500M转置K、1B普通K，均拆分历史/当前KV，保持原W8及敏感FP16例外。旧20-token批量、实际501/1001/510/1053历史结果只作为优化历史，不与新矩阵直接相除声称同条件提速。

CPU首token为本地HTTP/SSE首次报告已生成token的客户端耗时，另外记录首个可见文字；NPU为运行器内首个预测，含宿主转换、同步和采样，但不含HTTP传输。二者边界明确披露；llama.cpp的prompt_ms另外列出，不能当作NPU完整首token直接比较。decode两端均使用首个输出之后127个token的计时。首次建立缓存、加载时间和后续增量响应分开报告；加载不是清空OS页缓存后的冷启动。

性能记录每秒系统负载、温度、可用内存、swap；CPU另取独立llama-server进程CPU时间/RSS，NPU取运行器CPU时间/RSS和驱动分配。网页服务保持在线但必须空闲，CPU/NPU部署和测试共用排他锁。相同机器上的CPU与NPU不同时测速。

## 范围与计时

- 本轮只做纯文本，包含 embedding、全部 decoder、最终 norm/head、必要转换、同步和采样；不包括视觉编码、语音、并发、功率测量或换板。
- 有效历史分短历史、128、512、1024、2048 token，4096 为扩展档。用户最新指定512/1024为真实使用重点，优先验收这两档。这里是已经缓存的有效token数，不是字符数或静态分配容量。固定轨迹追加128步与自然EOS对话分开测；容量必须容纳历史、本轮新增输入和输出，不能用容量512假称测试history=512后再生成128。
- 长历史开发先采用静态容量768/1280，分别容纳512/1024缓存+20新增+128预测（最后一次预测无需回灌，实际占659/1171位置）。同时检查绝对RoPE位置、因果mask、KV读写、增量新算token数和容量边界。静态大图会处理空槽，其速度损失如实计入；后续容量切换/缓存迁移须单独验证，不把重建全历史冒充KV复用。
- 优先复原已有真实对话作为开发轨迹，实际长度如实标注：1B缓存510/1053、新增20；500M缓存501/1001、新增63/64。均可由768/1280容量容纳128步预测。精确512/1024的算子诊断与这些真实文本样例分别记录。
- 全程增量 KV；首轮预填充、追加消息的增量预填充、decode、冷加载分别计时。性能测试不写逐 token 大 logits；数值测试另行保存完整 logits/逐层 trace，不混入干净性能成绩。
- 每档至少五次，最终候选持续 30 分钟。记录温度、频率、负载、RSS、驱动分配、可用内存、swap 变化、释放后分配以及异常。
- 板端 CPU/NPU 测试使用同一排他锁，避免相互争抢；记录生产网页是否空闲及其常驻占用，出现并发请求的轮次作废重跑。

## 1B短序列的明确对标线（用户2026-10-12补充）

用户要求对标此前CPU约20多token/s、约0.23秒首token的实际对话体验。已核对[原始KV增量评测](../../docs/benchmarks/2026-10-10-kv-fan/KV缓存增量性能报告.md)：InternVL3-1B-Instruct Q8_0，两个A76（CPU6/7）、2线程、greedy，每项固定生成128 token。不是FP32参考实现，也不是重新处理整段历史。

| 实际输入token | 已缓存token | 本轮新算token | CPU decode token/s | 客户端首token秒 | 来源窗口 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 104 | 84 | 20 | 20.319 | 0.174 | 1024 |
| 104 | 84 | 20 | 20.315 | 0.173 | 4096 |
| 267 | 247 | 20 | 19.143 | 0.202 | 1024 |
| 530 | 510 | 20 | 18.257 | 0.246 | 1024 |

短历史研发参考线为约20.32 token/s及0.17–0.25秒级首token；用户提出的0.23秒作为体验目标，不能用它放宽CPU在同场景已做到约0.173秒的正式对照。延续此前15%速度余量，按历史短档暂算目标约23.37 token/s；若CPU调优后更快，目标随之提高。历史每格仅一次，正式验收须在同条件下重复至少五次，不能把历史点称为最优CPU已完成搜索的结果。

当前NPU开发候选为13.219 token/s；从该阶段成绩到20.32的数值目标仍需约54%提升，到23.37需约77%。这些只是目标距离，输入和工作量不同，不能作为同场景CPU/NPU实测加速比。当前NPU首token为2.731秒，包含空KV开始的49-token首轮逐token预填充，不含加载；CPU表中的首token是84个token已经缓存、仅追加20个token的客户端延迟，两者不能直接相除给出延迟慢多少倍。

下一轮优先实现并验证可跨用户轮次保留KV的测量入口及批量增量prefill：相同模型/模板/输入token、相同84个有效缓存token、同样追加20个token、同样128步预测，准备阶段不计入增量TTFT；两端分别核对缓存命中与新算token数。保留真实自然生成检查，固定轨迹只用于对齐工作量。容量必须至少容纳104+128−1=231个位置，当前NPU容量128不足以承载这一整项测试，需要增加容量并验收KV/位置/掩码。冷加载、首轮无缓存首字、后续有缓存首字分别列出，客户端链路开销与运行器时间分别标注。

优化优先级同时覆盖decode与首字：减少decoder/head计算和数据转换，提高decode；批量处理本轮新增token并复用历史KV，降低增量首字。已有逐tokenKV更新不等于已经实现高效批量prefill或跨请求会话缓存。整体目标仍为相同质量下超过对应CPU曲线，不以仅胜过上一版NPU作为达标。

## CPU 搜索范围

2026-10-12批量prefill阶段已落地：1B在容量256完成84缓存+20新增、128步、与CPU相同token输入轨迹的五轮比较。NPU A76宿主首字1.210→0.316秒，decode约12.60；CPU历史2线程A76配置重新五轮约20.25 token/s、首字0.174秒。500M容量128首字1.923→0.858秒，decode约14.05，尚未对齐其历史189-token输入。参见[批量Prefill与CPU对标](批量Prefill与CPU对标.md)。批量路径仍有1B首轮开发样例精度失败，不算完整质量达标；网页NPU会话、充分CPU调优和长历史/30分钟验收仍未完成。

2026-10-12 用户最终澄清：若历史 CPU 已测 Q4，则对齐 CPU/NPU Q4；否则主要优化 Q8。已核实 500M、1B 历史均为 Q8_0，没有 Q4 成绩。因此本轮以优化后的 CPU Q8 为对照、NPU W8 为主要优化对象，暂停 Q4 新试验及新建 CPU Q4 基线。现有最快实测 Q8 仍只是阶段结果，不能称线程/缓存等调优已全部完成。此前锁定的 FP16 来源在 `cpu-f16-sources.json`，仅保留供后续准备。

核对 llama.cpp 版本、构建参数和实际 ARM 指令；在 Q8 范围搜索 1/2/4/6/8 线程，单大核、两个大核及大小核组合。搜索可支持的 attention、KV 精度、batch/prefill 参数，明确不可用配置和原因。固定正常供电与散热，核对频率策略，不人为压低 CPU。

NPU INT4 首先核对编译器、目标芯片和板端实际执行是否支持；分别记录权重存储位宽、乘法执行类型、激活/KV 位宽以及高精度例外。W4 存储后解包为 W8/FP16 的路径必须明确标注，不能称原生 INT4 加速。先用真实模型线性层和单层图排查能力，再推进完整生成验收；小图通过不算最终目标达成。

先筛选，再为入围配置跑完整矩阵。每个模型、历史档位取最快的**质量合格** CPU 中位成绩，而非沿用旧的“两大核 Q8 约 27.5 token/s”。同输入输出长度比较真实墙钟耗时；CPU 与 NPU 不同量化允许正常差异，但必须通过同一质量门槛。

## 正确性门槛 v1

本节在当前敏感算子方案完成全模型验收、以及 CPU 配置搜索之前冻结。此前用于调试的问候和 lonely 陪伴样例不算留出集。留出集见 `quality-holdout-v1.json`，不用于校准或调参；一旦用其错误指导修复，必须明确转为开发集，并在下一次验收前另建留出集，不能继续称独立验收。

1. 执行正确性：将 NPU 实际导出权重交给独立 FP32 参考，在相同 token 轨迹比较；不得出现 NaN/Inf、V 归零或缓存错位。每场景完整 logits 相对 L2 ≤5%，逐步最低余弦 ≥0.99，最高分 token 一致率 ≥95%。逐层误差同时保存用于定位，不能以两层替代最终 logits。比较的词表、tokenizer、模板、RoPE、mask、位置必须一致。
2. 权重量化质量：同一独立留出轨迹相对较高精度参考，平均 KL ≤0.05 nat/token，参考文本困惑度上升 ≤5%；包括 CPU 量化候选。没有合格原始高精度权重时，先以现有反量化 Q8 权重为锚，明确这是相对 Q8 的增量误差，不能称相对训练原始 BF16 无损。
3. 自由生成：逐条展示实际回答，与同模型 CPU 参考对照。不得出现新增的系统性复读、无内容提前 EOS、明显答非所问。自然度、角色稳定、记忆各按 1–5 分评阅；均分下降不超过 0.25，任何一项不能有超过 1 分的个案下降。自动指标不代替人工评阅；未经评阅只能记“数值通过、质量待验收”。基线本身失败的中文案例单列，不掩盖也不归咎于 NPU。
4. 自定义 FP32 oracle 须与标准实现核对；自洽并非正确性证明。现有 llama.cpp tokenizer 检查和输出比较继续保留，后续补充固定轨迹 logits 校验。

数值阈值是本项目工程验收标准，不是所有 LLM 的通用标准。不因某方案更快而放宽；如需修订，另建版本、说明原因，并对 CPU/NPU 全部候选重新验收。

## 实施顺序

先在 500M 完成 V 归零、残差、head、Norm/softmax 的定位与完整生成。残差与 head 做 2×2 对照；逐层同时检查局部误差和累计误差。获得有效配置后迁移到 1B，重新校准和定位，不假设两个架构共享同一节点编号、V 修复或精度配置。

NPU 优化顺序：预计算 RoPE/mask、批量转换和缓冲复用；减少同步与重复量化；2/4 层融合与布局/GQA 优化；窗口容量分档；大矩阵与输出头；独立批量 prefill；最后探索 CPU/NPU 混合划分。每项记录精度、耗时、内存变化。CPU 仅分词/embedding/采样/调度与 CPU 承担 head/Transformer 运算的混合方案分别报告。

用户随后强调增加提速投入。本轮已经优先优化输出头，并用完整 token/logits 核对宿主 RoPE、mask、KV 拷贝改动。后续重点是 2/4 层融合、减少中间搬运、容量分档和批量 prefill；精度验证是每项加速的门槛，不再把所有精力用于无性能收益的低位误差打磨。对应量化档位的 CPU 配置继续正常调优。

## 达标定义与当前状态

两个模型在各核心历史档位的 decode 中位速度均超过最快合格 CPU 至少 15%；同输入输出长度端到端耗时更低；单列首字延迟，不以高速 decode 掩盖慢 prefill；30 分钟无崩溃、持续内存增长或明显退化。
