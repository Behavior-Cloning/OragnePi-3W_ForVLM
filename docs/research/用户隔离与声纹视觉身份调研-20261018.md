# 用户隔离、声纹与视觉说话人识别

2026-10-18。针对当前 USB 手机充电器供电、插电自动启动的 Orange Pi Zero 3W / A733。本文交付调研和部署设计，**没有安装或启用声纹、人脸、摄像头识别服务，也没有采集用户生物特征**。已部署的记忆检索原型另见《板端记忆迁移调研-20261018.md》。

## 建议先做什么

当前单主人使用，先建立可信的 owner/guest 会话开关、每人独立记忆空间。此模式算力成本最低，但“owner 模式”表示用户明确选择的会话模式，不能当作自动识别成功。家庭共享或需要自动切换时，再引入本地声纹；视觉先辅助判断“谁正在说话”，不宜一开始就全时运行复杂视听模型。

优先试验路线：VAD → 中文 CAM++ 或 WeSpeaker ResNet34 ONNX 声纹 → 已注册模板比对 → unknown/owner/guest 策略。多人同框时增加人脸跟踪及视听关联。声纹识别结果和“有权读取某人的长期记忆”是两个不同决定，不能直接等号。

## 六个概念不能混用

| 技术 | 回答的问题 | 能否直接绑定长期记忆 |
|---|---|---|
| 音色/声学相似度 | 两段声音听起来是否相似 | 不能；情绪、距离、噪声会改变相似度 |
| 说话人分段 diarization | 何时是 A 说话、何时是 B 说话 | 不能；A/B 常是本次会话的匿名簇 |
| 声纹验证 verification | 当前声音是否属于声称的已注册人 | 需要阈值、拒识、注册与可信会话策略 |
| 开集识别 identification | 在已注册人中是谁，或 unknown | 必须允许 unknown，不能强制最近模板 |
| 人脸识别 | 当前画面的人脸是否与注册模板匹配 | 只能说明画面中的人，不能说明他正在说话 |
| 视听活跃说话人检测 ASD | 哪个脸轨迹与当前音频说话同步 | 是关联证据，本身不提供姓名或授权 |

“屏幕前有主人”不意味着远处的声音也是主人。照片、视频、电视、机器人自身 TTS、多人重叠都可能造成混淆。单麦克风也不能凭左右方向猜对应的人脸。

## 候选与本板适配

### 声纹：先 CPU ONNX，NPU 后续再评估

- [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) 官方列出 Linux ARM64 支持，含 speaker embedding/identification API。官方 [speaker-identification.py](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/speaker-identification.py) 展示多段注册音频求平均、embedding manager、阈值搜索和 unknown；示例默认单线程 CPU。
- 该例默认阈值 0.6 **只是示例**，不能照搬成家庭环境验收值。应按实际麦克风、距离、噪声、注册人数校准分数和 top1/top2 margin。
- [WeSpeaker](https://github.com/wenet-e2e/wespeaker) 提供声纹、diarization、ONNX 预训练模型；[预训练文档](https://github.com/wenet-e2e/wespeaker/blob/master/docs/pretrained.md) 有中文 CNCeleb ResNet34 与 CAM++ 等。模型许可证随训练数据，代码许可不等于所有权重可任意发布。
- [3D-Speaker](https://github.com/modelscope/3D-Speaker) 有 CAM++、ERes2Net、音频/多模态 diarization。官方表 CAM++ 7.2M 参数、ERes2Net-base 6.61M、ResNet34 6.34M。优先拿小模型导出的 ONNX 做比较；不把整个 PyTorch 训练环境搬到板上。
- 当前板没有 NumPy/ONNX Runtime/PyTorch；需独立 venv 或 C++ runtime。sherpa 支持部分其他芯片 NPU，并不意味着支持 A733 的现有 NBG 路径。声纹模型导入 A733 要单独解决动态时长、算子、校准、输出精度，不应打断现有 LLM NPU runner。

### VAD、回声与采音

[Silero VAD](https://github.com/snakers4/silero-vad) 有 ONNX/CPU路径。VAD 只判断语音，不识别人；官方列出的其他机器延迟不能当本板性能。采音建议统一 16kHz 单声道，实际设备若48kHz需明确重采样和时间戳。

TTS播放期间先抑制记忆写入；完善 AEC 和参考音频消除后再验收打断功能。ASR字幕相同、唤醒词相同均不代表同一人。小于足够有效语音长度、削波、低信噪比及重叠说话进入 unknown；不能把静音补长当有效声纹样本。

### 视觉与视听关联

- 人脸检测/跟踪 → 人脸 embedding 只在轨迹初建、质量改善或明确切换时计算，避免每帧比对。可以先用低帧率检测、较高帧率轻跟踪；具体帧率待本板测试。
- [InsightFace](https://github.com/deepinsight/insightface) 是可参考的检测/ArcFace生态，但官方预训练权重限非商业研究；若最终产品发布，要另选可用权重或获取许可。
- [TalkNet-ASD](https://github.com/TaoRuijie/TalkNet-ASD) 明确目标是“画面中的这张脸是否在说话”，依赖音频和连续面部片段。官方demo默认训练/桌面栈，CPU需调整代码；不能宣称已有 A733 实时部署。
- 3D-Speaker 的 video diarization 是更完整参考，但也涉及检测、跟踪、音频特征、同步和聚类；第一版不推荐整套常驻。
- 简单嘴部运动+VAD门控可作为低成本实验，不能当身份验证或可靠活体检测。电视中的脸和声音可能同时同步，视听同步本身不抵抗重放。
- 必须使用同一单调时钟做音视频对齐。音频owner、视觉guest冲突，或多人同时动嘴时进入unknown；不能简单相加概率。分数没有校准前，也不能写成“置信度99%”。

## 资源预算：区分计算值、工程目标和实测

下表均为**尺寸计算或设计目标，尚无本板声纹/视觉模型实测**。

| 项目 | 可推导的成本或建议上限 | 说明 |
|---|---|---|
| 16kHz 单声道 int16，5秒环形音频 | 160000 bytes，约156 KiB | float32为312.5 KiB；不含采集/runtime缓冲 |
| 256维float32声纹，10人×3模板 | 30720 bytes，约30 KiB | 256维只是尺寸例子，实际读取模型输出维数 |
| CAM++ 7.2M参数 | FP32权重约27.5 MiB，INT8理论约6.9 MiB | 不等于ONNX文件大小、进程RSS或可用INT8模型 |
| 声纹服务初始资源目标 | 单CPU线程；RSS软预算256 MiB | 目标待测，超出先降频/按需加载，不承诺能达到 |
| 视觉服务初始资源目标 | 额外RSS不超过256 MiB；按唤醒事件启用 | 目标待测；模型和画面缓冲要计入 |
| 语音结束后的身份增量延迟 | 工程目标p95≤300 ms | 不含获得足够语音所需的时间，未测 |
| 对LLM干扰 | 相同温度/输入下TTFT和tok/s退化目标≤5% | 需混合负载A/B，单独跑快不算通过 |

身份通常需要累计一段语音，不能要求用户开口第一个字就可靠绑定。ASR可并行执行，但在身份确定前不能将私人记忆送入LLM、日志或流式输出；不确定则本轮按guest完成回答。不要先向LLM提供owner记忆再试图在输出阶段过滤。

板端可用内存约4.35 GiB、TF剩余约2.06 GiB是本轮实验前快照，不代表能无限叠加常驻模型。记忆检索约18–22 MiB进程RSS已实测，声纹/视觉需另外量；NPU约718 MiB驱动分配也不能替代整机内存核算。

## 身份与记忆状态机

1. 开机、会话超时、换人、模型故障：默认 guest/unknown；如果用户明确选择个人owner模式则显示该模式。
2. 显式注册：用户触发注册，录入多段、跨位置的语音，必要时录入人脸。模板归属使用服务端随机 user_id，不用“我叫某某”的语音转写做授权。
3. 在线识别：先检查音频质量、非TTS、无重叠；比较已注册模板，满足阈值、margin及连续窗口稳定性后给出候选。
4. 记忆读取：仅可信会话与已批准身份才能查询对应namespace；可单独设置“允许称呼/偏好”与“私人事实”范围。
5. 长期写入：要求身份稳定且用户确认“记住”；unknown仅有本会话临时内容，不自动升为owner长期记忆。
6. 换人或冲突：终止当前私人响应，清除该会话动态KV、候选记忆和历史；相同固定system KV可以保留，绝不能复用前人的动态KV。
7. 更正/撤销：撤销模板立刻失效；提供撤销身份但保留记忆、或删除该用户记忆的独立选择。更新模板必须重新确认，不能用未知来访者持续自动“适配”主人的声纹。
8. 退出/服务错误：回guest，不因识别服务超时就回owner。

读取门槛和写入门槛分别设计，写入更保守。声纹、人脸均只作为便捷识别信号；需要敏感记忆访问时保留可信端确认。模板匹配不是密码或高安全认证的替代品。

## 服务边界和部署顺序

建议本机三个职责：音视频输入服务产生时间戳和质量指标；identity service只输出受信 user_id/guest、证据种类、过期时间；memory service 按该身份构建上下文。LLM只收到最终文字和受限记忆，不负责决定身份。

客户端传来的 namespace、username 或“我是主人”不能直接成为数据库查询权限。Web界面即使在局域网也需可信会话映射；本地原型CLI的namespace参数仅供研究，不是已实现的鉴权。

部署分三步：

- A：先 owner/guest 显式切换、namespace/会话隔离、撤销、审计和失败回退。当前记忆库已经验证数据层隔离，生产HTTP鉴权与UI尚未接。
- B：独立目录安装CPU ONNX声纹候选，离线固定音频先比 embedding parity、RSS和RTF，再在自愿注册样本上校准。设置单线程、短队列、队列满时放弃本轮身份计算；不占用LLM NPU队列。冻结模型、预处理和阈值版本。
- C：只有多人使用确实需要时，接摄像头轨迹/人脸辅助，再测ASD。视听原始流默认仅短环形缓冲，尽量只存已确认模板；提供可见的采集状态和撤销入口。

所有开发代码/导出在 Windows F盘/WSL；ARM64 wheel或交叉构建产物再经Windows部署。为适配USB常供电，采音事件常驻、重模型按需唤醒；不依赖外接电池或更改供电电路。关闭开关应走正常关机流程，SQLite FULL也不能保证任意拔电下TF控制器绝不丢数据。

## 后续板端验收协议

不能用公开数据集EER直接宣称家中准确率。注册样本与测试样本需不同录制时段；阈值在开发集选定，最终测试集冻结。

- 语音：主人及自愿参与的访客、近/远距离、安静/电视背景、正常/小声、单人/重叠、机器人TTS及手机重放。分别报告误接受FAR、误拒绝FRR、unknown比例、身份切换延迟，不能只报整体正确率。
- 视觉：侧脸、遮挡、背光、多人同框、主人在画面但访客说话、画外音、手机播放视频；单独报告说话人关联准确率和错误绑定率。
- 系统：冷启动与热态p50/p95、CPU线程时间、RSS/PSS、模型与缓存占盘、有效语音时长、RTF、LLM并行退化和温度。失败时持续保持guest。
- 隔离：双人交替对话100轮，查询/更正/删除互不影响；换人后历史、摘要、动态KV不能跨namespace；含服务重启和身份模型不可用场景。
- 质量门槛先以“私人记忆错误绑定零例”为小规模验收目标，同时报告样本量。即使0/100也不能宣称零风险：独立试验粗略95%上界约3%，要证明更低风险需更大样本和更严格场景。
