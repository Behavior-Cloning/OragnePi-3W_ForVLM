# MiniCPM-V 4.6：A733 NPU 部署测试

**结论：文本解码器已在 NPU 上完成实际运行；当前原型约 1.31 token/s，31-token 输入首 token 约 17.55 秒，尚不适合作为现有模型的替代。图像编码器尚未部署，这不是完整 VLM 图像链路的测试。**

修正版能输出连贯中文，但单层误差仍偏大，模型名称回答也有错误，精度尚未验收。以下性能是这份 FP16 初始移植的实测值，不能当作该模型在 A733 上经过充分优化后的上限。

## 测试条件

- 板卡：Orange Pi Zero 3W / Allwinner A733，6×A55 + 2×A76，约 5.7 GiB RAM。
- 24 个语言层、所有注意力/MLP/归一化和完整词表输出均通过 VIPLite NPU 图执行；CPU 负责 embedding 查表、RoPE 参数生成、缓存搬运和 argmax。
- 模型在每个版本的三轮测试期间常驻；结束后释放 NPU。原有 CPU llama-server 保持运行，未修改主线程服务。
- 输入 31 token，固定生成 16 token；第 0 轮与其后的 2 轮分别保留，下面速度使用后两轮中位数。样本量很小，不能报告可信的 P95。
- batch=1，容量 128，逐 token 预填充，未复用固定 system 前缀；权重、激活和 recurrent state 均为 FP16。
- 首 token 时间从文本 token 送入运行时开始，排除加载时间；不含语音、图片编码、网络或界面显示。

CPU 指标只涵盖该进程，不是全系统 CPU 占用。进程 RSS 约 6 MiB，**不包含 NPU 驱动分配，不能当成模型总内存**。温度只记录轮次边界的 zone0，未测连续峰值；未做长时间压力测试。

基线输出是乱码。修正版的原始输出为：

> 你好！我是MiniCP4，一个简短的AI助手。很高兴认识你

同一输入的官方 FP32 输出开头为：

> 你好，我是MiniCPM系列模型，由面壁智能和OpenB

首 token 相同不代表精度达标。两条自由生成序列从后续 token 开始使用不同上下文，不能将后续逐位置匹配率直接称作准确率。当前仅为一条问候语的运行检查，没有完成任务准确率评测。

## 模型结构核实

原始 safetensors 参数总数 **1,300,428,016**，不是根据模型名称估算：

| 权重分组 | 参数数 |
|---|---:|
| language_model | 752,161,600 |
| vision_tower，含内部压缩模块 | 522,299,312 |
| 外部 merger | 25,967,104 |

语言部分 24 层：18 层 GatedDeltaNet 线性注意力，6 层完整注意力；词表 248,094。它与现有 Intern 1B 同为 24 个语言层，不能据此认为层数更低。视觉部分包含 27 层和窗口压缩结构，本次没有将其部署到 NPU。

## 编译和精度问题

1. **短轴卷积求和触发编译器异常。** ReduceSum 表达在 NBG 生成阶段出现浮点异常；改写成等价的四项乘加后可以编译，真实 layer0 的 CPU 结果与官方实现对齐。
2. **FP16 门控归一化丢失小稳定项。** 中间结果方向基本一致、幅度却严重放大。将稳定项改成平方比值，避免直接使用很小的 FP16 常数后，layer0 隐状态相对 L2 误差从 153.3% 降至约 15.0%，仍未达标。
3. **CPU 参考初始化也做了核对。** meta 初始化后的非持久化 RoPE 缓冲区必须重新初始化。修正后，31-token 输入下自定义 FP32 堆栈相对官方实现的最大绝对差约 0.000145，首 token 一致。早期失败日志保留，未将错误参考计入 NPU 精度结论。

| NPU 探针 | 平均 API 时间 | 输出相对 L2 误差 | 说明 |
|---|---:|---:|---|
| 线性核心：FP16 逐元素乘加/求和 | 4.770 ms | 2.44% | 合成输入，一次状态更新 |
| 线性核心：FP16 矩阵乘法 | 6.704 ms | 0.098% | 合成输入，一次状态更新 |
| 线性核心：显式 FP32 导出 | 43.070 ms | 0.086% | 已核对 I/O 是 FP32；不能据此保证内部每一步均为标准 FP32 累积 |
| 完整 layer0：修正后 FP16 | 22.941 ms | 14.98% | 真实权重、零初始状态；单层检查 |

核心误差和整层误差的输入、比较张量不同，不能直接横向比较。上述单层数字不是完整模型 decode 速度。

仅在量化配置里填写 float32、仍使用 quantized 导出时，实际 I/O 会成为 FP16；这一无效 FP32 对照已单独记录。显式使用 `--dtype float32` 后，才验证到 FP32 I/O。它明显变慢，误差改善有限。

## 提速尝试与限制

已尝试将修正版矩阵权重替换为 per-channel INT8、保持原来的 FP16 图。多个解码层和词表分片均在 SDK VerifyGraph 阶段返回不支持的配置，因而停止剩余批量编译，没有进行 W8 板上测速。**这只说明本次直接替换方案失败，不代表 A733 不支持 W8。**

当前慢的主要因素是逐 token 预填充、未融合的 24 层调用，以及大词表的 FP16 输出矩阵。现有 Intern 1B 的高性能路径使用了不同的量化、融合和缓存策略；本次结果不能作为两种模型完成同等优化后的公平对比。

后续需专门适配 W8/定点激活与浮点敏感算子之间的转换、校准真实会话状态，并设计批量预填充。应先解决精度，再开展更大范围的性能优化。FP32 全量替换不能直接当成快速修复。
