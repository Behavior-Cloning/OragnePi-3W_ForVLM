# 流式/非流式链路与 LLM 长时压力测试（2026-10-18）

> 2026-10-19 口径纠正：下表 0.836 秒是旧版端点假设下的估算，不能作为真实用户说完→首字实测。0.106 秒来自重复文本命中 CPU LLM 缓存，且没有同时跑整条语音链。新版以真实 VAD 事件触发、按实时速率重放音频并保持 NPU 文本模型常驻，结果见 [全链路常驻测试报告](全链路常驻测试报告-20261019.md)。

## 版本边界

- 非流式基线：`continuous_dialogue.py`，GTCRN + Silero VAD + Paraformer，保留在原目录，不覆盖。
- 流式版本：`research/audio-streaming/streaming_dialogue_v1.py`，版本标记 `streaming-dialogue-v1`，链路为 KWS → GTCRN → Streaming Zipformer Small → LLM。
- 压力测试版本：`research/audio-streaming/llm_stress_v1.py`，版本标记 `llm-stress-v1`。
- LLM 为板卡现有 CPU `llama-server` 的 Qwen2.5-1.5B Q4；本轮不是 NPU LLM 测试。

## 两条链路对比

| 指标 | 非流式优化版 | 流式 Zipformer v1 |
|---|---:|---:|
| 降噪 | GTCRN，开启 | GTCRN，开启 |
| ASR | Paraformer，端点后整段识别 | Zipformer Small，80 ms 级持续解码 |
| 端点后到 LLM 首段文本，中位数 | 1.025 s | 0.736 s |
| 估算真实说完到 LLM 首段文本，中位数 | 1.125 s（100 ms 端点估算） | 0.836 s |
| 首个部分识别 | 无 | 1.501 s（仍在说话期间，不代表最终文本） |
| ASR 结果 | 之前三条中两条准确，一条人名错误 | 三条中两条完全一致，一条人名出现“朱胜伟素至”错误 |

流式链路已经可以在用户说话过程中产生部分文本；但当前安全策略仍在端点后才把最终 ASR 文本提交给 LLM，避免把未完成句子送给模型。流式 ASR 因而改善了 ASR 的持续可用性和端点后延迟，但还没有实现“边说边让 LLM 预生成”。

本轮流式三轮逐轮端点后首段延迟为：1.143s, 0.676s, 0.736s；第一轮较慢，三轮样本不足以宣称稳定达到 1 秒。

## LLM 长时压力测试

固定输入格式为：`system prompt + 召回记忆 + 本轮用户输入`，不把历史对话不断追加到上下文；6 个生活场景循环 60 轮，包括提醒、天气、饮水、家电、日程和菜谱。每轮最多生成 48 tokens，串行请求，轮间等待 150 ms。

| 指标 | 结果 |
|---|---:|
| 总轮数 | 60 |
| HTTP/推理错误 | 0 |
| 首段文本延迟 P50 | 0.106 s |
| 首段文本延迟 P95 | 1.158 s |
| 完整回复延迟 P50 | 1.627 s |
| 回合温度峰值 | 64.2 °C |
| llama-server RSS | 1112–1131 MiB |
| 负载（1 分钟 loadavg） | 0.50–1.85 |

60 轮连续运行没有异常退出或 HTTP 错误，RSS 基本稳定；温度峰值约 64.2°C，长时间压力下已经明显高于短测试的约 50°C。需要把散热、限频和更长时间（例如 30–60 分钟真实语音交互）纳入上线前验收。当前压力测试只压 LLM，没有同时运行视觉模型、TTS 或 NPU VLM，因此不能代表全系统最大热负载。

## 结论和下一步

两条链路都保留。默认建议先使用流式 Zipformer 做实时 partial/VAD，再在端点后提交最终文本；非流式 Paraformer 保留为高准确率回退和回归基线。若要把“真实说完到首字”稳定压到 1 秒以内，下一步应测试：端点前稳定 partial 的置信度门控、LLM 请求预启动/取消机制，以及 LLM 线程与音频线程的 CPU 亲和性隔离。不能直接把未经确认的 partial 送给 LLM，否则会增加错答风险。
