# LLM 冷/热缓存与 NPU 常驻 KV 复核（2026-10-19）

> 2026-10-19 实板纠正：旧 resident 的复用条件要求整个既有 history 是新 prompt 的前缀；动态记忆/历史变化时会清空 KV，不能仅凭 system 放在最前面就认为它一直复用。本次已修复为保留共同完整 prefill 块，并通过 5 组 cached/reset 全 logits 逐位比较。当前板端语音＋NPU 文本实测见 [全链路常驻测试报告](全链路常驻测试报告-20261019.md)。本文旧 HTTP/CPU 数字只作历史记录。

## 结论

前一轮压力测试的首段文本 P50 为 0.106 秒，不能代表第一次请求。60 轮中前 6 轮分别是 6 个场景的第一次 prompt，属于冷 prompt；后 54 轮重复相同的 system＋记忆＋用户组合，命中了 llama-server 的 prompt/KV 缓存。完整回复耗时还受到输出长度影响。

生产方向应采用常驻模型，并把固定 system prompt 放在 KV 前缀最前面。现有实验性的 NPU resident HTTP 已经支持常驻 NPU 模型和跨请求 KV 复用；它不是当前 8081 CPU llama-server 的替换服务，仍需经过产品质量、板端独立服务和长时间并发验收。

## 为什么首段延迟跨度大

| 分组 | 轮数 | 首段文本 P50 | 范围 | 完整回复 P50 | 范围 |
|---|---:|---:|---:|---:|---:|
| 冷 prompt：每个场景第一次请求 | 6 | 1.165 s | 1.054–2.192 s | 2.819 s | 1.841–5.673 s |
| 热 prompt：重复场景且命中缓存 | 54 | 0.106 s | 0.105–0.108 s | 1.438 s | 0.770–4.660 s |
| 混合统计 | 60 | 0.106 s | 0.105–2.192 s | 1.627 s | 0.770–5.673 s |

冷 prompt 的额外时间主要是新 prompt 的 token 评估和 CPU 调度；模型本身已经常驻内存，所以这里的“冷”不是重新加载 1.1 GiB 模型。热 prompt 的首段文本很快，但完整回复仍可能变长，因为生成 token 数不同：短回答约 0.77 秒，较长回答约 4.6–5.7 秒。

因此，之前的 P50/P95 混合值把冷请求和命中缓存的重复请求放在了一起，容易让 0.106 秒看起来像所有请求都能达到。后续报告应同时给冷首请求、热首请求和完整回复三组数据。

## NPU 常驻模型与 system/KV 复用

项目已有 `npu/kv-cache/resident_session.c`、`resident_worker.py` 和 `resident_http.py`。模型加载后驻留在板端，HTTP/分词网关在工作机，token 和事件通过 SSH 传给板端 NPU；它是实验性开发接口，不是生产 8080 CPU 网页的自动替换。

已保存的板端 NPU resident HTTP 证据：

| 模型 | 层数/容量 | 首轮引擎 TTFT | 后续轮 reused token | Decode 速度 | 板端 RSS | 驱动 NPU 内存 |
|---|---:|---:|---:|---:|---:|---:|
| SmolVLM 500M Q8 | 32 / 1280 | 1.000 s | 55、88 | 18.55–19.07 tok/s | 24.5–26.0 MiB | 约 670 MiB |
| InternVL3 1B Q8 | 24 / 1280 | 1.070 s | 84、147 | 14.43–14.49 tok/s | 20.4–24.2 MiB | 约 732 MiB |

固定 system prompt 位于序列化 prompt 的最前面，因此后续请求的 `reused_tokens` 包含 system 前缀以及此前保留的对话前缀。resident session 还验证了前缀变化会重置 KV，窗口溢出会删除完整旧轮，关闭时 `driver_bytes=0`。

这组 NPU 结果和 CPU 压力测试不能直接做同一张 P50 表：NPU 证据是 5 轮开发 HTTP 对话，500M/1B 模型、提示模板和输出长度不同；CPU 压力测试是 60 轮 Qwen2.5-1.5B Q4。它们能证明两件不同的事：CPU 测试揭示了冷/热缓存行为，NPU resident 测试证明了常驻 KV 和 NPU decode 路径已经存在。

## 负载与资源

CPU LLM 60 轮压力测试：

- 无 HTTP/推理错误。
- llama-server RSS 约 1.13 GiB，基本稳定。
- 1 分钟 load average 从约 0.50 逐步升到约 1.85。
- 回合末温度峰值约 64.2°C。
- 这组温度是 CPU Qwen2.5-1.5B 压力，不是 NPU resident 的温度结论。

NPU resident 证据中，1B 引擎 RSS 约 20–24 MiB，但 NPU 驱动占用约 732 MiB；500M 约 670 MiB。NPU 运行并不等于整机完全不占 CPU，分词、HTTP/SSH、协议、采样和部分调度仍在 CPU 上运行，不过主 decoder/head 计算在 NPU。

## 部署建议

1. 所有模型进程常驻，避免按句加载。
2. 固定 system prompt 永远放在 prompt 前缀，先建立 system KV，再追加召回记忆和当前用户输入。
3. 语音链路使用流式 Zipformer；端点后把最终文本提交给 resident NPU LLM。
4. 先做 NPU resident 500M/1B 的真实中文 system＋记忆＋用户压力测试，再决定默认模型；不要把固定 feedback benchmark 的 15.5 tok/s 直接当作真实对话速度。
5. NPU 与 CPU 语音前端并行时，必须重新测 CPU 核占用、温度、驱动内存和 30 分钟稳定性；当前 NPU HTTP 证据不是这项完整验收。
