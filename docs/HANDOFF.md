## 1. 项目定位与交付目标

本项目以 Allwinner A733 / 6GB Orange Pi Zero 3W 为硬件平台，研发可本地运行的桌面陪伴机器人。核心用途是情感陪伴、角色扮演、日常聊天，后续扩展图片理解、音频理解和实体设备交互。当前交付是软件原型与推理研究，还不是具备完整音画感知、动作和电源管理的成品机器人。

用户优先关心对话自然、角色和称呼稳定、能记住和接受更正、不复读，以及低首字延迟和流畅解码。公开指标优先参考 HellaSwag、TextVQA，不能用知识问答分数替代陪伴体验。相关场景见[第一阶段评测](陪伴机器人第一阶段评测.md)和 `tests/companion/`。

工程目标是在保留可用 CPU 服务的同时，让 NPU 承担完整语言模型主要计算、减少 CPU 占用并提高速度。用户要求完整深度、对应量化档位、优化过的 CPU 对标和真实 KV 复用；局部探针、失败质量候选或慢 CPU 参考不能作为“已达标”的证据。

## 5. 两条服务链路：生产CPU与实验NPU

### 板端CPU网页

```text
电脑/手机浏览器
  → 板卡 :8080 Python网页/API网关
  → 板卡 127.0.0.1:8081 llama-server（CPU）
  → 当前选择的GGUF模型
网页网关 → 板卡回环 :8083 控制器（切模型/窗口、回滚、资源采样）
```

这是已部署在板卡上的服务，不要求工作站常开。最近确认配置为Qwen2.5-1.5B Q4 / 4096；历史URL为 `http://192.168.88.29:8080/`，不是实时在线承诺。systemd服务是 `opi-vlm-web`、`opi-vlm-model`、`opi-vlm-control`，配置见 `configs/systemd/`。

网页代码入口：`src/vlm_chat/server.py`、`control.py`、`system_prompt.txt` 和 `web/`；模型清单/哈希在 `configs/vlm-models.json`。安装与切换入口为 `scripts/install_vlm_on_board.sh`、`scripts/select_vlm_model.py`。旧[部署手册](SmolVLM网页部署.md)中的默认InternVL是当时快照，不是最新默认模型。

### 实验NPU网页

```text
浏览器 → 工作站 resident_http.py / tokenizer
       → SSH token/事件流 → 板端常驻C运行器
       → 全深度NPU decoder + 输出头 + 常驻KV
```

代码为 `npu/kv-cache/resident_http.py`、`resident_worker.py`、`resident_session.c` 和 `resident_chat.html`。已对500M/1B做实板跨轮、裁剪、reset、停止和浏览器验证，详见[HTTP验证](../npu/kv-cache/HTTP多轮接口验证.md)。实验页刷新不持久保存聊天；它没有替换生产8080，也不能把它的已验证能力自动算到新Qwen NPU候选上。

CPU承担分词、embedding查表、调度或采样与CPU承担decoder/head计算必须区分；后一种须标为混合计算方案。当前运行器在板端也做编排和greedy选择，不能把所有非NPU工作都归到工作站。

## 6. 网页功能、会话和上下文的实际语义

- 支持新建/切换多会话、流式回答、停止、上传/粘贴图片（需视觉模型）。图片压缩到最长边768像素。
- 历史文字和图片保存在当前浏览器的IndexedDB `orange-vlm`，无固定过期时间；不是服务器账号数据库。换浏览器、IP/域名或端口会切换存储来源，清网站数据会丢历史。
- 每条会话和当前会话都可删除；有确认框，生成期间禁删/禁切换。删除历史不训练/修改权重，也不等于安全擦除推理进程KV。
- 可选已下载模型及1024/2048/4096/8192窗口，点击“应用并加载”；配置对整块板共享，加载失败回滚，不同访客不能各自拥有独立模型。
- 超窗时移出最早的完整问答轮次，保留system和当前问题；旧记录仍在浏览器，后续不再提交模型。没有自动摘要或长期记忆；单条最新输入仍超窗则报错。
- 每次提交保留的上下文文本不等于全部重新计算，llama.cpp可以复用匹配的KV前缀。换模型、窗口、模板或裁剪导致前缀变化时可能重建缓存。
- 单次回复最多256 token，窗口同时容纳输入/输出；长度截断有提示。单消息4000字符、API请求16MiB、最多1024条消息是另行限制。
- 单推理槽，忙碌或加载时提示冲突；无账号认证，只面向可信局域网。尚无自动跨设备历史同步。
- 有端到端耗时、首个文字片段、后端token/s及约3秒刷新资源面板；没有精确剩余token条。浏览器首字不等于引擎首token。

详细语义以[对话保存与上下文](对话保存与上下文.md)和源码为准。配网、实体开关机键、重启键尚未产品化。

主机生成ONNX与参考输入，厂商ACUITY校准/量化/编译NBG，再上传板端VIPLite执行。主要代码均在 `npu/kv-cache/`：

| 环节 | 入口 |
| --- | --- |
| 导出/局部输入 | `qwen_fused_fixture.py`、`single_decoder_fixture.py`及各模型fixture |
| 量化/编译 | `compile_weight_int8.py`、`compile_lowbit_stack.py`、`compile_fused_stack.py` |
| 完整运行/核对 | `run_full_model.py`、`validate_full.py`、`exported_greedy_reference.py` |

| Qwen效率筛选 | `qwen15_group_search.py`、`summarize_qwen15_speed.py` |

KV保存每层已处理位置的K/V；decode只追加新token，首次建立历史和本轮新增prefill单独计算。旧500M/1B已验证跨请求前缀匹配、reset、最后预测token尚未回灌的计数及窗口边界，见[常驻KV核对](../npu/kv-cache/常驻模型与跨请求KV验证.md)。Qwen目前只有短容量内增量decode，尚不能沿用上述长历史/HTTP验收结论。

旧模型已有批量prefill、两层融合、compact GQA、部分转置K、KV分段和hidden缓冲复用等实验；不是每个模型/容量都采用相同布局。静态容量含空槽，容量和有效history需分别记录。报告文件名中的 `w8`、源目录中的 `c128` 可能沿用旧命名，以manifest、variant和实际输入为准。

## 10. 当前1.5B攻关结果

模型固定为Qwen2.5-1.5B-Instruct，纯文本；28层、hidden1536、12个Q头/2个KV头，完整词表151936，输出头拆4片。详细见[适配记录](research/Qwen15适配实验-20261014.md)、[效率报告](research/Qwen15提速-20261015.md)和[专用交接](research/Qwen15-HANDOFF.md)。

- CPU Q4_K_M短prompt功能检查：44输入token，自然EOS共18输出，约10.2769 token/s，中文正常。这是单次检查，不是重新调优后的最终CPU基线；也不能直接与NPU固定64输出算正式加速比。
- NPU从上述Q4_K_M反量化后再次做W4/A16，权重导出为INT8容器内的低4bit数值；尚无原生打包INT4执行/访存证据。
- 已修正strict mask有效分数低于旧哨兵的问题，并用动态行最小值避免极端负值毁坏校准。V投影逐通道路径近乎归零，改DFP W4后第0层首token的V执行误差约0.047%、hidden约0.127%；只是局部执行修复。
- 全28层 `w4-vdfp-sensitive` 能出中文，但仍有“我今天，我有Q，谢谢我”等复读。相同导出常量在主机FP32运算也复读，原CPU Q4正常；说明导出/二次量化已引入退化，尚未分离head、V和其他矩阵各自贡献。
- 当前最快研究路径是单层图、`--decoder-group 28 --group-head --fast-greedy`、性能模式关闭trace、宿主绑6/7核。ctx128、44prompt、64输出，五次中位 **5.032149 token/s / TTFT 8.042304s**，全部输出token一致，质量仍失败。
- 本次筛选起温约29.2–32.5°C，属于凉态短试验，不是旧40–50°C低温档或55–<65°C中温验收。驱动分配707732408字节（约675MiB），释放后0；宿主进程CPU约单核1%，不能写成整机1%。
- group4样本总响应约99.09%在NPU API内部；该API包括驱动等待、同步、搬运，不等于算术单元占用。第26层孤立重放约89.2% busy cycles在fullconnect、前三个矩阵约79.4%；不能外推为全模型占比或DDR带宽已满。

## 11. RWKV研究和指标解释

只保留 `VisualRWKV-v7.00-0.4B` 一个视觉候选，见[选型与来源](research/RWKV与1.5B选型-20261014.md)。0.4B是语言骨干标签，视觉另有SigLIP SO400M、DINOv2 Large、SAM ViT-B；权重约2.40GiB，运行峰值更大。不要按“0.4B”直接判断可以轻松塞进板卡。

HellaSwag测试生活情境后续的常识选择，不直接测共情；TextVQA测试读图中文字并结合画面回答，不等同中文OCR专项。RWKV7相对RWKV6公开语言结果有提升，但纯语言1.5B分数不能套用到VisualRWKV0.4B。候选公开TextVQA约41.05，MobileVLM V2-1.7B约52.1，跨团队协议未统一，仅供选型。

RWKV用递归状态而非随history增长的Transformer KV，可能节省长期状态内存，但不是无损无限记忆。官方VisualRWKV v7主模型依赖CUDA扩展，旧 `app_cpu.py`实际为v5演示；公开生成示例也不能直接证明高效状态复用。先在工作站拆视觉/投影/递归模块，对照完整logits及状态更新，再评估板端部署。当前没有板端RWKV速度或视觉准确率结论。

## 12. 后续评测必须遵守的口径

完整计划见[验收协议](../npu/kv-cache/完整模型验收计划.md)，这里列接管时容易混淆的要点：

1. 每个模型都测完整语言深度及输出头，CPU/NPU对应量化档位。CPU取预先声明配置搜索内最快合格方案；不限制CPU线程或选慢FP32参考来制造优势。
2. 核心场景是已经缓存512/1024有效token，再新增32/64/128（含模板）；正式旧协议生成128次预测、127个decode间隔，容量768/1280。先准备KV再计增量TTFT，不重复全历史prefill。
3. 固定CPU反馈轨迹用于性能与逐步logits对齐，自由生成/自然EOS另测；二者不能互相替代。
4. 区分模型加载/冷启动、历史准备、新增prefill、引擎首token、HTTP首个完整文字和整轮总响应。没有清页缓存验证的加载不称断电冷启动。
5. 温档按响应开始时测量：低40–50°C、中55–<65°C优先，高65–80°C暂缓；允许运行时自然升降温，记录起止/峰值/频率，不能当恒温实验。
6. 执行参考与原模型质量是两道门槛：既有执行门槛L2≤5%、min cosine≥0.99、argmax≥95%；量化质量KL≤0.05、PPL比≤1.05，并逐例审查自由输出。原始高精度参考缺失时须标明Q8/Q4锚点。沿用协议或预先版本化，不因快而放宽。
7. 留出集不能用于调参；一旦用失败指导修复，转为开发集，下一次换独立数据。JSON顶层 `passed`可能只表示任务跑完，需看逐例数值和回答。
8. 同轮直接采样CPU/RSS/PSS、实际换页、I/O、温度、NPU driver内存，说明覆盖率。整机CPU八核合计100%与进程单核100%不同；RSS/driver映射不可直接相加。
9. 最终目标为同质量各核心场景NPU中位decode至少胜最快CPU 15%，端到端更快并通过30分钟稳定/多轮/真实音频共存；目前未达成。功耗和真实DDR流量没有完整实测，不虚构瓦数、能效或带宽利用率。

## 13. 板端访问、容量与故障处理

最后地址 `192.168.88.29`、用户 `root`；DHCP可能变化。使用现有本机认证，不在Git写密码。Wi-Fi客户端隔离、VPN和不同子网会影响SSH；掉线不等于过热或TF故障，先检查实际网络/内核/文件系统证据。

所有板端操作串行使用主机 `npu/results/board-host.lock` 和板端 `/run/opi-npu-kv-benchmark.lock`。当前研究工作树的host lock是指向原项目同名锁的符号链接；迁移/新建worktree时必须保留共同锁目标，不能各自创建独立锁后自称互斥。带锁runner不要再套同一host锁造成死锁。查看 `lslocks` 时 `WRITE`是持有、`WRITE*`是等待，不重复启动队列。

历史上板端曾ENOSPC，TF剩余2–3GiB等数值都是快照，不能用于新部署容量预算。每次检查上传图、完整logits与至少512MiB额外预留；只清理已逐文件SHA核验本地备份的板端诊断副本，并保留恢复清单。模型、生产服务、唯一数据和用户文件不删除。RSS小不代表NPU没有占RAM，swap已用不代表此刻换页。

关机按系统正常poweroff并等待完成；硬件按键方案要先确认PMIC/电平/引脚。关机后的Linux程序不能响应普通GPIO来冷开机，需单独验证硬件唤醒或电源控制。具体待办见[TODO](TODO.md)，不直接照其它Orange Pi型号引脚焊接。
