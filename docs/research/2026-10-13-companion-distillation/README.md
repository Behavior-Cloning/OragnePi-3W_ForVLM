# 端侧陪伴模型：短句自然聊天的数据、训练、蒸馏与评测调研

调研日期：2026-10-13。面向 Orange Pi Zero 3W 项目；本文件是研究与实验设计，不是已经完成的训练实验报告。

优先级更新：按本次讨论，**依赖教师 logprob 的 on-policy 分布蒸馏降为低优先级探索**。主线为高质量短对话 SFT、商用教师文本改写与偏好训练。开放权重教师通常更便于取得所需概率，但并非逻辑上只有开源模型才能提供；以实际接口为准。学生先生成、教师再文字点评的迭代训练不需要 logprob，仍可保留。

**目标：回复简短、自然，能接住日常话题，保持角色稳定。** 当前优先纯文本、多轮陪伴；视觉、音频和复杂推理不是本阶段主目标。重点考虑现有 SmolVLM-500M、InternVL3-1B 系列，以及可作为语言能力对照的 Qwen2.5-1.5B-Instruct、Qwen3-1.7B 非思考模式。VLM 型号中的参数规模包含视觉部分，不能直接当作语言骨干参数量进行训练成本比较。

研究方法：查阅原始论文、作者仓库及数据卡；核对公开版本的规模、来源和获取方式。**未逐条审计或完整下载这些数据，未运行微调，未实测本文训练吞吐。** 原始资料会更新，实际训练须固定数据与模型 revision。引用索引见文末及同目录 `sources.md`。

## 1. 推荐结论

最值得先投入的路线是：

1. 用少量人工校准样例明确“短而自然”，建立独立评测集；先做提示词基线。
2. 从中文日常对话、人设、多轮情绪回应中整理约 3 万条训练窗口，先做 **SFT + LoRA**。
3. 让学生自己展开多轮对话，由商用教师标出具体问题、改写局部回答，形成 **迭代 SFT / 在线采样的 DPO**。
4. 只有在奖励与人工偏好一致、同一提示下候选回答有可区分质量时，再试 **GRPO**。
5. 决赛在实际量化、实际上下文与端侧部署上验收。浮点训练模型的提升不能代替板端效果。

**不建议把心理咨询数据直接作为主训练集，也不建议第一轮就上 GRPO。** 前者容易得到“我理解你的感受＋一串建议＋你愿意说说吗”；后者容易奖励长篇、套话、逢迎或固定句式，计算也更贵。

商业 API 可以很好地做教师，但应准确区分：文本改写蒸馏、偏好反馈训练、逐 token 分布蒸馏。能调用聊天 API，不代表能实施论文中的完整 logits on-policy distillation。

| 决策 | 本项目建议 | 理由 |
| --- | --- | --- |
| 第一目标 | 自然度、人设稳定、接话能力 | 与用户需求一致，先不要用知识问答榜单替代 |
| 回复风格 | 日常多数 1–2 句；按语境允许更短或更长 | “短”是偏好，不应成为截断或空洞回应 |
| 数据骨架 | 中文口语素材 + 定制人物/场景多轮 | 现成数据很少同时满足中文、短回复、机器人角色 |
| 第一训练 | BF16 LoRA SFT | 约 1B 规模优先简单稳定；显存紧张再 QLoRA |
| 第二训练 | 学生轨迹 + 教师修正 / DPO | 直接覆盖学生实际犯错的位置 |
| 商业教师选择 | 小规模盲测选教师，不按品牌直接定胜负 | 最强推理教师不一定最会写自然中文短句 |
| GRPO | 条件性探索 | 先证明奖励可靠、收益超过更便宜的 DPO |
| 长期记忆 | 外部事实存储/检索 + 多轮训练 | 微调不能替代每个用户的动态记忆 |

## 2. 把“短、自然、陪伴”变成可训练的目标

### 2.1 推荐风格规格

日常回复初始设定为：多数 1–2 句、约 10–60 个汉字；这只是数据筛选与评测的初始范围，**不是每句话硬性下限/上限，也不是 token 数**。问候、告别可以更短；用户明确要求解释、讲故事时可以更长。

具体目标：回应当前信息；允许轻微幽默；记住已给信息；不在每轮追问；不把闲聊变成解决方案；不机械复述；不无端给用户起昵称；角色喜欢什么、如何说话前后一致；被纠正后自然修正。

| 用户输入 | 期望方向（示例，不是唯一标准答案） | 应避免 |
| --- | --- | --- |
| 今天啥也没干，有点废 | “那今天先算休息日呗，别急着给自己判分。” | 五条自律建议、心理分析、连续追问 |
| 终于把那个 bug 修了 | “可算逮到它了！今晚能安心收工了。” | 长篇解释调试过程、假装知道具体 bug |
| 别问我问题，陪我待会儿 | “好，不问。你想说的时候我就在。” | “那你现在是什么感受呢？” |
| 我其实不喜欢咖啡，之前说错了 | “记住了，那咖啡从你的菜单里划掉。” | 后面仍推荐咖啡、质疑用户前后矛盾 |
| 嗯 | 根据前文简短承接，必要时结束这一轮 | 每次都“还有什么可以帮助您？” |
| 你刚说你怕冷，怎么又说喜欢冻着？ | 承认矛盾并修正角色表述 | 编造越来越复杂的理由 |

这些表达也不是人人喜欢。正式风格金标准必须由目标用户筛选，避免把训练者个人口味当作普遍自然度。

### 2.2 陪伴不等于咨询，不等于动漫角色模仿

心理咨询数据主要教倾听和引导；角色数据主要教人物知识与口吻；日常陪伴还需要无目标闲聊、话题跳转、轻松调侃、短回应、结束对话。应分项采样，不能依赖一个名字里带“共情”的数据集解决全部问题。

机器人还应区分可执行能力与角色表达。例如没有控制接口时，“我帮你关灯了”属于能力事实错误。评测对此单列，不与虚构角色喜好混淆。

## 3. 数据集调研与适配分析

下面的“公开”指存在作者发布入口，不代表所有数据均采用同一种开源许可。代码、模型、数据的条款可能不同；获取条件仅作资料事实记录，不展开合规讨论。

### 3.1 中文日常对话与人设：优先考察

| 数据集 / 来源 | 语言、规模与生成方式 | 适合做什么 | 本项目的主要问题与处理 |
| --- | --- | --- | --- |
| **LCCC** [D01] | 中文；base 6,820,506 段对话，其中 3,354,232 单轮、3,466,274 多轮；large 12,007,759 段。社交平台等语料整理 | 大量口语、短句、生活话题、接话素材 | 噪声、语境缺失、网络梗、过时表达；无稳定机器人角色。先筛出少量高质量片段，不全量灌入。优先 base；仓库声明研究用途 |
| **CPED** [D02] | 中文 40 部电视剧；11,835 段对话、132,762 条 utterances；情绪、人格、对话行为等标注 | 中文情绪接话、角色差异、多轮承接 | 剧情冲突、舞台式表达、多角色关系不能直接转成 user/assistant。只选不依赖画面的两人自然片段。按剧集划分防泄漏 |
| **RoleBench / RoleLLM** [D03] | 中英；100 个角色、168,093 条样本；含教师生成的角色知识和风格数据 | 人设条件化、口吻稳定、角色问答 | 虚构人物知识不等于生活陪伴。挑中文短对话，减少背景设定背诵；角色和模板做留出 |
| **WildChat-1M** [D04] | 真实用户与模型交互，多语言；项目称百万级，当前所查过滤版数据卡列 **837,989** 条 | 真实口语输入、模糊输入、中英混用、话题跳转 | 大量是任务型助手请求，模型回复未必短。筛中文日常输入，重新制作符合目标风格的回答；只保留训练必要字段 |
| **PersonaHub** [D05] | 人物描述资源，不是对话集；早期公开 20 万 persona，后来发布更大描述集 | 构造多样用户背景与场景种子 | 不能把 persona 直接当聊天样本；避免“精英人物”偏置；只需要少量覆盖普通日常生活的人物 |

CPED 的计数口径：train/valid/test 对话数分别为 8,086/934/2,815，话语数为 94,187/11,137/27,438。不要把单条 utterance 当作一段完整对话。

WildChat 的“真实”是用户输入来源真实，不表示回答为真人写作，也不保证目标陪伴风格。其当前数据卡数量与项目百万级名称不同，下载时应以固定 revision 实际行数为准。

### 3.2 情绪回应：有价值，但控制占比

| 数据集 / 来源 | 规模与来源 | 推荐用途 | 不宜直接照搬的部分 |
| --- | --- | --- | --- |
| **EmpatheticDialogues** [D06] | 英文，约 25,000 段基于情绪情境的对话，众包人类参与 | 短共情回应、接住生活事件；少量翻译并中文改写 | 翻译腔、固定表达；长程人设覆盖不足 |
| **ESConv** [D07] | 英文 1,300 段情绪支持对话，8 类支持策略；另有 FailedESConv 196 段负例 | 学会何时倾听、何时提供建议；构建“过度建议”反例 | 目标是支持过程，不是随意闲聊；仓库注明学术研究用途。失败对话不是现成 DPO 配对 |
| **SoulChatCorpus** [D08] | 中文；2024-06 公开版 **258,354 段多轮对话，1,517,344 轮**；由咨询问答扩展、含教师合成 | 从中筛选简短倾听、温和回应，重写为日常风格 | 长咨询回复、套话、不断追问。论文训练样本数与公开对话/轮数不同，不应混用 |
| **CPsyCoun** [D09] | 中文；3,134 段通过咨询报告重建的多轮对话 | 支持结构、特定情绪场景的补充 | 重建合成而非原始真人逐字记录；公开 CPsyCounD 与需申请的原始报告 CPsyCounR 不同 |
| **PsyDTCorpus / SoulChat2.0** [D10] | 中文；5,000 段、90,365 轮；训练 4,760 段，测试 240 段；由少量咨询案例与问答种子合成 | 风格一致性、数字分身构建方法参考 | 固定咨询师风格，平均长对话，容易把陪伴机器人变成咨询师 |
| **PsyQA** [D11] | 中文咨询问答；仓库有样例，完整数据需申请 | 提取情绪情景，不宜作为主回答来源 | 长答案、问答而非自然交谈、获取门槛；本报告不把它当立即可下载的完整语料 |

初始建议：**明确带咨询师口吻的数据，经筛选和改写后占全部训练窗口不超过约 5%–10%**；更广义的日常情绪接话可占约 15%。这是待实验的配比，不是论文证明的最优值。

### 3.3 英文/日文多轮对话：借鉴结构，不作为中文主粮

| 数据集 / 来源 | 已核对特征 | 用途与局限 |
| --- | --- | --- |
| **DailyDialog** [D12] | 英文日常多轮；人工整理，情绪和交际意图标注 | 话题覆盖、短句互动；偏教学式对话，翻译后不一定像当代中文聊天 |
| **PersonaChat / ConvAI2** [D13] | 英文，参与者根据给定 persona 对话；不同加工版本计数不同 | 稳定人物事实的经典训练/诊断来源；容易“自报家门式”硬插设定，需筛选 |
| **BlendedSkillTalk** [D14] | 约 7,000 段；融合人格、知识、共情；人类对话中一方获得模型建议 | 比单一共情集更接近混合聊天能力；与 PersonaChat、EmpatheticDialogues 等来源有交叉，划分时处理关联 |
| **MSC** [D15] | 多 session 人类对话；sessions 1–4 提供约 237k 训练 examples、25k 验证 examples，另有 session 5；含摘要任务 | 外部记忆、跨次会话承接的设计参考；237k 是派生训练样本数，不是独立长对话数 |
| **RealPersonaChat** [D16] | **日语**；公开 13,583 段对话、408,619 条话语、233 位参与者 persona；真人背景与主观对话评价 | 真实人格和交谈满意度研究价值高；不能误当中文集。少量人工审校翻译，优先参考其评测设计 |

翻译数据先抽样比较“忠实翻译”和“保留情境、重写中文互动”两种方式。日常自然度通常不能只用翻译正确率来筛选。

### 3.4 偏好与通用能力数据：辅助，不替代陪伴标准

| 数据集 / 来源 | 已核对规模、反馈 | 本项目的用法 |
| --- | --- | --- |
| **UltraChat** [D17] | 仓库称约 1.57M 合成对话；常见精选子集是另一版本 | 少量保留指令理解与基本常识；不要让通用助手长篇风格淹没陪伴风格 |
| **UltraFeedback** [D18] | 63,967 个提示，各约 4 个模型回答；教师细粒度评分 | 可练偏好管线，但应重新按“自然、简洁、人设”审查；使用修正过的评分版本，不把原始四回答与二元衍生集混为一谈 |
| **HelpSteer2** [D19] | 21,362 条回复记录：训练 20,324、验证 1,038；每 prompt 两个回答；人工评 5 个属性，另发布直接偏好标注 | 更适合研究人类反馈、偏好一致性；复杂度/冗长度是描述维度，不应简单“越高越好”。优先直接 preference 子集而非随意相减制造偏好 |

不推荐以通用 helpfulness 总分决定陪伴质量。“详尽、有结构、信息多”的回答在助手任务里可能胜出，在“我下班了”这样的日常交谈里可能明显失败。

### 3.5 独立评测资源：默认不进入本项目训练集

| 基准 / 来源 | 已核对内容 | 如何使用 |
| --- | --- | --- |
| **CharacterEval** [E01] | 中文；77 个角色、1,785 段多轮、23,020 条样本；13 个指标、4 个维度 | 角色稳定性诊断；不能将公开评测题改写后训练再宣布该榜提升。其 reward 模型也不等于本项目可信的最终裁判 |
| **LoCoMo** [E02] | 当前 `locomo10.json` 公开 10 条长对话；早期论文规模与此不同；合成多 session | 测记忆检索、更新、回答；独立对话簇很少，不能按每道问答完全独立计算置信区间。图片只提供链接/描述等，不是完整随包图片集 |
| **LongMemEval** [E03] | 500 道题、5 类记忆能力；S 约 115k tokens，M 更大；有 oracle；建议 cleaned 版本 | 评外部记忆系统。直接截到 1k tokens 属于改造实验，不能冒充原版得分 |
| **LongMemEval-V2** [E04] | 作者 2026 年发布；451 题，强调超长期、类似“有经验同事”的交互 | 后续长时记忆研究；与当前短句日常陪伴存在领域差异，不因更新就优先采用 |

当前最值得实际抽样的组合：**LCCC、CPED、RoleBench、EmpatheticDialogues、ESConv、MSC**；SoulChat 少量筛选；WildChat 主要补真实用户输入。CharacterEval 和自建日常集做主要评测，记忆基准作为专项。

## 4. 数据工程：比换损失函数更先决定效果

### 4.1 第一版 30,000 条训练窗口建议

这里一条“窗口”包含角色设定、若干历史轮次、一个或多个被监督的 assistant 回复；不是 30,000 个独立用户，也不等于 30,000 个长 session。

| 类别 | 比例 | 窗口数 | 核心内容 |
| --- | --- | --- | --- |
| 日常闲聊 | 35% | 10,500 | 吃饭、工作、天气、爱好、随口感叹、无聊、结束聊天 |
| 人设与口吻 | 20% | 6,000 | 设定保持、换话题后保持、被纠正、不过度表演 |
| 日常情绪 | 15% | 4,500 | 小开心、小失落、疲惫、吐槽；倾听优先，不强求建议 |
| 记忆与指代 | 15% | 4,500 | 已知喜好、否定更新、时间、跨 session 摘要、信息缺失 |
| 基本指令/知识 | 10% | 3,000 | 用户真的要求解释时能解释，避免微调后通用能力塌陷 |
| 修复与降级 | 5% | 1,500 | 识别错词、承认没听清、纠正上一轮、别乱编执行结果 |

按**有效 assistant 监督 token**再次统计配比，防止少量长咨询回答占据大多数梯度。去重、筛选前的原始下载量不算有效训练规模。

### 4.2 推荐处理流水线

1. 每个候选源先人工审阅 60–100 段，记录可用率、改写率、长度、语言与角色问题。
2. 保留可追溯 ID、原始来源、版本、改写教师版本；规范 speaker，但不随意把多角色剧本交替映射为 user/assistant。
3. 按情境筛选；剔除离开画面无法理解、完全依赖前文缺失、机械套话、固定广告等样本。
4. 精确哈希去重，再做近重复与模板簇检查；关联数据源一起分组。
5. **先按原始对话/剧集/角色/模板族划分，再切窗口、翻译、教师改写**，防止同一内容衍生版本跨 train/test。
6. 重写时保留事实和语境，缩短推销式/咨询式表达；将原文与改写同时抽检，拒绝教师添入不存在的关系、行动或记忆。
7. 用学生自己的 tokenizer 统计长度。训练时采用正确 chat template，只对选定 assistant token 算损失，屏蔽 user/system/padding。
8. 多条对话 packing 必须阻止跨样本错误注意力，或用框架确认支持的隔离方式；不能只插 EOS 就假定完全隔离。

建议记录：`source_id, source_revision, conversation_id, persona_id, template_family, split, messages, memory, target_style, teacher_version, rewrite_reason, reviewer_status`。训练导出与 provenance 分离，避免多余标签被学进回复。

### 4.3 长度控制的正确方式

数据里要同时出现短承接、自然追问、无追问的回应、用户主动结束。用目标风格和高质量示例教模型何时停止。

不要通过把所有回答机械裁到 30 字来“造短回复”：这会制造半句话、不完整意思和错误 EOS 学习。也不要为了控制长度把所有回答变成“好呀”“嗯嗯”；评测必须同时判断是否回应了具体内容。

### 4.4 动态记忆不能只靠微调

长期记忆建议分为稳定角色卡、用户明确事实、最近对话、按需检索摘要。训练样本应呈现正确的检索内容、缺失内容、过时内容与更新冲突。

例如“以前喝咖啡，现在不喝了”要保留更新时间和当前有效值。把旧记忆原封不动拼入 prompt，然后希望模型自己猜哪个有效，容易导致不稳定。先评检索召回与过时信息率，再评回答是否正确使用记忆。

## 5. 训练方法：它们不是互斥的选项

**SFT/DPO/GRPO 是目标与学习方式；LoRA/QLoRA 是参数更新与内存技术。** 可以 SFT+LoRA，也可以 DPO+LoRA、GRPO+LoRA。QLoRA 的 NF4 训练基座也不等于板端 INT4 权重格式。

| 方法 | 需要什么数据/接口 | 优点 | 主要成本/风险 | 本项目判断 |
| --- | --- | --- | --- | --- |
| 提示词 + 示例 | 少量人设与示例 | 零训练，建立最低成本基线 | 吃上下文；小模型可能遵循不稳 | 必做 |
| SFT | 目标风格的高质量回答/多轮 | 直接教口吻、长度、基本行为 | 模仿数据缺陷；过拟合、遗忘 | **第一优先** |
| 教师序列蒸馏 | 教师写出的回答 | 商业 API 易实现、跨 tokenizer 方便 | 学教师路径，未覆盖学生错误状态 | SFT 数据来源之一 |
| 拒绝采样 / RFT | 学生多候选 + 筛选器 | 实现简单，可先验证奖励质量 | 只学选中结果，低通过率时昂贵 | DPO/GRPO 前的廉价对照 |
| DPO | 相同上下文下 chosen/rejected | 不需训练时在线 rollout，通常比 RL 易调 | 偏好不准、长度偏置、分布过时 | **第二优先** |
| 在线采样迭代 DPO | 当前学生候选 + 新偏好 | 逐轮覆盖实际学生错误 | 采样/教师预算，数据版本管理 | 适合本项目 |
| GRPO | 每提示多候选 + 可重复评分 | 不需 PPO 式独立 critic，直接优化目标 | 奖励投机、组内无差异、rollout 贵 | 奖励成熟后试 |
| PPO | rollout、奖励、value/critic 等 | 灵活、可处理序列奖励 | 工程与显存成本高，稳定性复杂 | 首轮不优先 |
| GKD / MiniLLM 型分布蒸馏 | 学生轨迹上教师概率信息 | 比单个序列分数提供更细反馈 | 教师可访问性、词表对齐、实现成本 | 白盒教师可研究；文本 API 不等价 |
| 全参数微调 | 与上面目标配合 | 更新能力强 | 优化器内存、更易遗忘，需要较多调参 | LoRA 达瓶颈再比较 |
| 从零预训练 | 大量高质量文本与算力 | 完全控制底座 | 不适合当前投入与目标 | 不推荐 |

### 5.1 SFT 与 LoRA 的起跑配置

SFT 最小化目标 assistant token 的负对数概率。先训练自然的最终回答，不需要把教师长篇推理过程放进陪伴回复。

建议起点（待实验，不是通用最优）：LoRA rank 16/32，作用于 attention 与 MLP 的线性层；学习率试 5e-5、1e-4、2e-4；1–3 epoch；有效 batch 约 32–64 个窗口；最大序列 1024/2048，覆盖当前使用长度。先小样本验证梯度、EOS、模板，再正式训练。

VLM 纯文本阶段通常先冻结视觉塔和连接器，训练语言部分；检查框架是否正确处理 text-only 输入。纯文本改善可能影响原有视觉响应，后续恢复视觉目标时应加入少量视觉回放并回归验证。

LoRA 合并一般不改变推理网络拓扑，但会改变权重分布。已有 NPU 量化校准不能默认继续适用。

### 5.2 DPO：偏好必须是同一道题下的比较

对同一上下文 x 的优选 y+ 与劣选 y−，标准 DPO 优化学生相对参考策略的概率比差异：

`loss = -log sigmoid(beta × [(log π(y+|x) - log πref(y+|x)) - (log π(y−|x) - log πref(y−|x))])`

建议让当前学生每个提示生成 2–4 个回答，再由教师比较；教师必要时补一个修正答案。没有清晰优劣就标 tie，不硬造偏好。beta 可小范围试 0.05/0.1/0.2，以固定开发集选择，不把训练 reward 当最终质量。

FailedESConv 的失败对话与另一段成功对话往往不是同一上下文，不能直接一段 chosen、一段 rejected。适合提取失败类型，再构造同前缀候选。

### 5.3 GRPO：陪伴任务的瓶颈是奖励，不是能否运行

每个提示采 G 个候选，典型组内优势为 `(reward - 组均值)/(组标准差 + epsilon)`，结合策略比值裁剪等目标；具体 KL、归一化及长度处理须固定实现版本。组内都得到同样评分时，基本没有有用的相对学习信号。

建议先用 G=4、小批次测试。奖励包含相关性、自然度、人设、正确使用记忆和重复问题，**长度仅作条件性约束，不按“越短越好”加分**。有明显事实矛盾的回答不能靠语气讨喜获得高总分。

先冻结独立开发集，检查奖励提升是否伴随人工胜率提升；监控候选多样性、组内奖励方差、套话率、长度与 EOS。若训练分数提高但人类不偏好，停止扩量，先修奖励。

PPO、ORPO、SimPO、KTO 等还有不同的偏好训练选择，但本项目暂没有证据表明扩大算法清单比整理日常数据更有收益。首轮保留 SFT/DPO/GRPO 三条可解释对照即可。

## 6. 商用教师与 on-policy distillation

### 6.1 四种接口能力对应四条路线

| 教师能提供什么 | 能做什么 | 不应如何命名 |
| --- | --- | --- |
| 根据上下文生成理想短回答 | 序列级蒸馏、SFT | 不能仅因教师强就叫 on-policy |
| 阅读学生完整回答并评分、排序、改写 | 学生轨迹上的迭代 SFT / DPO / RLAIF | 不是完整 token 分布蒸馏 |
| 对学生给定前缀上的指定 token 求 logprob | 在满足词表和估计器条件时做采样式 OPD/KL 估计 | 不是拿教师自己生成序列的 logprob 直接替用 |
| 对学生每个前缀返回对齐的完整/足够概率分布 | GKD 等更直接的分布损失 | top-k 残缺分布不能未经处理当全词表 KL |

GKD 针对学生自生成序列上的分布失配；MiniLLM 研究 reverse KL 和 on-policy 优化 [A05,A06]。完整分布不是所有估计器的绝对必要条件，但**必须获得损失真正需要的、学生访问状态上的教师概率**。不同 tokenizer 的逐 token KL 不能直接相减，需要额外序列/词表对齐方法。

一般文本 API 最实际的路线是：

`当前学生 → 自己展开对话 → 教师指出具体问题/局部改写/比较 → SFT 或 DPO → 新学生重新采样`

可称“基于学生轨迹的迭代蒸馏”，并明确使用的是文本反馈。教师打分再 GRPO 属于 AI 反馈强化学习；也不要把参考策略 KL 与教师知识蒸馏混为一谈。

### 6.2 推荐商用教师选择方法

不凭印象宣称某个厂商当前最强。选择 3 个可用候选 API 版本，例如一个强中文聊天候选、一个强指令/综合能力候选、一个成本较低候选；确切版本与价格在启动试验时锁定。本报告不提供未核实的即时型号排名或价格。

用 100 个场景、相同短回复要求，人工盲评：能否接话、是否过度建议、角色一致性、纠错、能否产出可供小模型学习的简洁回答。再给 100–200 对已有回答，让教师做裁判，测它与人工偏好的吻合程度。

**生成教师、训练奖励裁判、最终测试裁判尽可能分开。** 生成最好者未必评分最可靠。教师遇到模糊场景应允许不确定/tie；要求指出证据，不把冗长评价当作准确评价。

教师输出可以采用结构化字段：`problem_type, evidence_turn, revised_reply, preference, confidence`。教师看到角色卡、有效记忆和学生历史；不要让教师自行补写不存在的用户经历。

### 6.3 第一轮迭代设计

1. SFT 学生在 2,000 个训练场景各生成 4 个单轮分支；另采一小批 6–10 轮真实学生轨迹。
2. 教师标出失败位置，生成局部修正；对清晰优劣做偏好配对，对“都不好”单独处理。
3. 混入原有 SFT 数据，防止每轮纠错导致通用聊天遗忘。
4. 训练后用新 checkpoint 重新采样，记录 rollout policy ID。连续使用很旧轨迹就不再贴近当前策略分布。
5. 先比较 1–3 轮的边际收益与教师成本，不预先承诺迭代越多越好。

训练的是自然最终答案；教师的诊断说明不默认作为机器人应输出的内容。

## 7. 训练资源、时长与成本预算

### 7.1 训练位置与显存

在工作站 GPU 上训练，板卡做部署验收。以下为**容量规划建议，不是已测显存峰值或显卡兼容保证**；取决于实际语言骨干、序列长度、batch、激活检查点、attention 内核及框架版本。

| 更新方式 | 约 0.5B | 约 1B–1.7B | 约 3B |
| --- | --- | --- | --- |
| BF16 LoRA SFT，1k–2k context | 8–16GB 显卡可试小 batch | 优先 16–24GB；24GB 通常是便利起点 | 优先 24GB，必要时小 batch/检查点 |
| QLoRA SFT | 能进一步省基座内存，但未必更快 | 12–16GB 可作为起步探索；24GB 余量更大 | 16–24GB 探索，实际需压测 |
| 全参数 AdamW | 16–24GB 起步较方便 | 24–48GB；1.7B 在 24GB 下不能保证 | 48–80GB 或分片/offload |
| DPO LoRA | 16–24GB 优先 | 24GB 优先；参考 logprob 可预计算 | 24–48GB 更宽裕 |
| GRPO LoRA | 24GB 做小规模试验 | 24–48GB，取决于 rollout 引擎及并驻模型 | 48GB 或拆分推理与训练更便利 |

BF16 权重粗略占 `2 × 参数数` 字节，1B 约 2GB（十进制）。全参数 Adam 混合精度训练常按每参数约 12–16 字节估权重、梯度、优化器/主权重状态，**尚未计激活、工作区和碎片**；实现可能不同。

LoRA 降低的是可训练参数与优化器状态，反向传播激活仍需内存。GRPO 不用独立 critic 不等于没有额外显存：生成 KV、推理引擎副本、策略/参考模型都会占用。API 教师不占本地大模型显存；本地白盒教师可能反而成为最大内存开销。

预算充足时，1B 左右先用一张 24GB 卡跑 BF16 LoRA，比为省少量内存一开始引入 QLoRA 更容易定位问题。主机建议 32–64GB RAM、足够 SSD 空间，数据预处理与 checkpoint 可按约 100GB 项目余量规划；这不是所有方案的最低要求。

### 7.2 训练时长必须按 token 算

设首轮 30,000 个窗口，平均实际处理 768 tokens，2 epoch：

`处理量 = 30,000 × 768 × 2 = 46,080,000 tokens`

| 假设实测训练吞吐 | 纯训练计算时间 | 加 20%–50% 评测/保存等开销的规划区间 |
| --- | --- | --- |
| 1,000 processed tokens/s | 12.8 小时 | 15.4–19.2 小时 |
| 3,000 processed tokens/s | 4.27 小时 | 5.1–6.4 小时 |
| 6,000 processed tokens/s | 2.13 小时 | 2.6–3.2 小时 |

**上述吞吐仅做敏感性计算，不是 4090 或任何 GPU 的实测成绩。** 多轮历史与 prompt 虽不算监督 loss，仍参与前向/反向计算；重复窗口与 padding 也有成本。实际按训练器累计 token 和 wall time 校准。

启动前进行 100–200 个训练 step 的小规模标定：预热后测有效吞吐、峰值显存、padding 占比、保存时间，随后重新计算完整预算。数据整理、人工标注和教师 API 等待通常比首轮 SFT 更难压缩。

### 7.3 DPO / GRPO / OPD 的额外开销

DPO 每个偏好样本有两个回答及参考概率，不能照搬 SFT 每条样本时长。冻结参考概率可离线预计算，但必须与同一参考 checkpoint、模板和截断规则一致。

示例：2,000 prompts × G=4 × 平均 96 输出 tokens = **768,000 个生成 tokens / 轮**。如果 rollout 的总有效吞吐分别是 50/200/500 tokens/s，仅生成约需 4.27/1.07/0.43 小时；不含 prompt prefill、教师调用、反向训练和串行多轮。仍是假设，不是硬件实测。

固定 96 是预算上限附近的示例，真实短回复应自然 EOS。批量总吞吐与单会话 tok/s 必须区分，不能拿端侧 20 tok/s 直接估计 GPU 批量训练效率。

GRPO 第一轮可先做数百至 2,000 个提示的试验，确认奖励有用后扩量。分布蒸馏还需要教师对学生前缀的评分计算；本地大教师的前向可能成为主要时间和显存成本。

### 7.4 API 与人工成本

API 预算使用实际输入/输出统计：

`费用 = 输入 tokens / 10^6 × 输入单价 + 输出 tokens / 10^6 × 输出单价 + 其他实际计费项`

例如一轮 20M 输入、2M 输出，设单价为每百万输入 2、输出 8 个货币单位，则 56 个货币单位。**价格为演示变量，不对应任何商业产品报价**；缓存、批处理、重复生成、重试、推理计费另按实际账单记录。

短输出不一定便宜：反复传完整历史进行教师审阅时，输入可能占大头。每个场景记录累计消耗，比较“每提升一个人工胜率百分点的成本”。

人工评测例：200 对完整对话、每对平均阅读评分 3 分钟、2 位评审，约 20 人时，另加分歧仲裁。不能把“只有 200 条”误认为几十分钟完成。

### 7.5 为什么不从零训练

仅作数量级说明：按 1B 参数、20B 训练 tokens、稠密 Transformer 粗估 `6ND`，约 1.2e20 FLOPs。在持续有效 100 TFLOP/s 的假设下，纯计算约 13.9 天；还未包含数据工作、故障、消融，且 **20B tokens 不保证得到好用的现代聊天模型**。现成底座后训练更符合本项目需求。

## 8. 评测：便宜可重复，也能反映真实聊天

### 8.1 三层组合

| 层级 | 测什么 | 频率 |
| --- | --- | --- |
| 自动规则 | 错角色名、违反明确禁问、事实更新、空白/截断、重复片段、超长、错误动作声明 | 每次 checkpoint 快筛 |
| 校准过的模型裁判 | 自然度、相关性、角色一致性、情绪回应；输出依据 | 开发集批量评测 |
| 人工盲评 | “更愿意与哪个继续日常交谈”，并记录具体失败 | 教师选择与最终候选决赛 |

BLEU/ROUGE、困惑度可作为诊断，但不能主导自然聊天选型。同一句“今天好累”有很多优秀回应，标准答案词面重合度很低也可能更自然。

### 8.2 数据划分与评测规模

建立三套独立集合：训练情景种子、开发集、冻结测试集。初期建议开发集 100 段，冻结测试 200 段，每段 6–10 轮；最后胜负不明显时扩到约 400 段或更多，而不是反复看同一测试题调参。

冻结测试初始 200 段可按以下分层，每层单独报告：

| 场景 | 段数 | 检验点 |
| --- | --- | --- |
| 普通闲聊、话题跳转 | 50 | 会不会接话，是否助手腔 |
| 轻度情绪与分享小事 | 30 | 是否过度建议、重复安慰 |
| 人设稳定 | 30 | 角色事实和表达风格是否一致 |
| 记忆、指代、事实更新 | 30 | 新信息覆盖旧信息，不虚构经历 |
| “嗯/哈哈/不知道”等短输入 | 20 | 不冷场、不机械追问 |
| 用户纠错、歧义、口语识别错误 | 20 | 能否自然修复 |
| 告别、沉默、明确不要建议 | 20 | 能否尊重节奏并自然结束 |

正文已公开的示例属于训练/开发设计资料，**不应再计入真正未见测试集**。正式冻结题由独立场景与表达实例生成，记录版本且隔离训练访问。

### 8.3 固定前缀测试与自由多轮测试必须同时做

固定前缀：各模型收到完全相同的历史，方便定位同一问题；但看不出自身回答造成的后续状态偏移。

自由多轮：模型保留自己的历史，用户模拟器按目标和已发生对话回应；可发现越聊越乱。需要相同情景、种子和模拟器版本，但不强求逐字相同后续用户输入，否则容易出现答非所问的无效轨迹。人工抽查模拟器是否过度配合或故意刁难某模型。

用户模拟器不能同时决定训练奖励和最终胜负。终局人类评价看完整对话，不只挑最漂亮的一轮。

### 8.4 打分尺度与失败定义

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 自然度 | 模板/客服腔，明显不适合此刻 | 通顺但平淡或略生硬 | 像自然接话，语气与上下文合适 |
| 相关与承接 | 答非所问或无视关键内容 | 回应主题但遗漏细节 | 明确接住当轮信息、指代清楚 |
| 角色稳定 | 身份/设定矛盾 | 大体一致，偶有飘移 | 多轮一致，不硬塞人设 |
| 情绪适配 | 误判、训话、过度表演 | 礼貌但套路化 | 分寸适当，支持方式符合用户意愿 |
| 简洁适量 | 长篇无关或短到没内容 | 稍冗长或略空泛 | 信息刚好，需要解释时不惜字 |

单列二元严重失败：重要人设矛盾、显式更新后仍用旧事实、无依据的用户经历、系统性复读、非预期语言切换、持续截断、虚构已执行动作。长回复比例、追问比例用作分布诊断，**不要求一律为零**。

可在开发阶段用综合分辅助筛选：自然度 30%、承接 25%、角色 20%、情绪 15%、简洁 10%。这是初始偏好权重，正式选型仍看分项、严重失败率和人工 A/B，不用一个加权平均掩盖角色崩溃。

### 8.5 模型裁判怎么校准

先选 100–200 对人类已标注回答，候选 A/B 匿名、顺序随机，抽样交换顺序重评。记录与人工多数意见的一致率、各场景分歧、位置偏置、长度偏置；给裁判允许 tie 的选项。

例如裁判总爱选 150 字解释而人类更喜欢 25 字接话，就先修 rubric，不急着用它大规模生产奖励。可暂设约 75% 人类一致率为继续自动化的检查线，但它不是普遍充分条件，还必须看分项与样本不确定性。

最终裁判尽量与教师不同，且不知道候选来自哪个模型/算法。只对少量关键分歧调用第二裁判，把人工集中在高价值决策上。

### 8.6 统计与显著性

人工 A/B 建议两位评审独立判胜/平/负，关键分歧仲裁；记录 `胜率 = (胜 + 0.5×平)/总数`，同时展示原始胜平负数量。

置信区间按**对话或场景簇** bootstrap，不把同一段的 10 个回答当 10 个独立用户。对于独立、无平局、胜率接近 50% 的简单二项近似，100 对约 ±10 个百分点，400 对约 ±5 个百分点；存在平局、相关性时需重算。因此 52% 对 48% 不足以凭小样本宣布胜出。

先冻结质量门槛。可将“自然度胜率有可靠提升，重要角色/记忆失败无恶化”作为初始选择原则。具体 2%/5% 失败率门槛应在试点后、正式候选搜索前确定，不在看到结果后放宽。

## 9. 模型选择：分阶段淘汰，保留质量—延迟折中

### 9.1 学生候选

| 候选 | 必须回答的问题 |
| --- | --- |
| 现有 SmolVLM-500M | 中文短聊差距能否靠数据修补，还是底座表达容量不足？视觉冻结后语言训练是否稳定？ |
| 现有 InternVL3-1B | 语言部分能否达到日常自然度，是否保留现有部署路径与视觉能力？ |
| Qwen2.5-1.5B-Instruct | 中文基础是否更适合；额外模型内存、速度和 NPU 适配代价能否接受？ |
| Qwen3-1.7B 非思考模式 | 短回复能否稳定无多余思考文本；chat template 与训练目标是否一致？ |

不预判任何候选胜出。现有 VLM 可以保留为视觉入口，专门语言模型可能更适合聊天，但双模型驻留/切换会增加系统成本；先测再决定。

### 9.2 推荐实验矩阵

| 阶段 | 候选数量与试验 | 淘汰依据 |
| --- | --- | --- |
| A：无需训练 | 4 个底座，各 2–3 个短聊 prompt；小开发集 | 中文表达、基本人设遵循、实际延迟 |
| B：小 SFT | 留 2 个；相同 3k–5k 高质量窗口，LoRA | 是否确实能学到自然风格、是否遗忘 |
| C：正式 SFT | 2 个底座，完整约 30k 数据；少量超参 | 完整开发集与分项质量、训练成本 |
| D：蒸馏/偏好 | 最佳 1–2 个 SFT；迭代 SFT、DPO 对照 | 固定教师预算下的净增益 |
| E：可选 GRPO | 最佳模型、已校准奖励；小规模 | 相比 DPO 是否有可靠增益 |
| F：最终板端 | 2–3 个最终候选、实际部署量化 | 人工决赛、速度、内存、稳定性 |

控制变量：相同场景与角色卡、相同有效记忆预算、相同回复长度目标；各模型采用正确官方模板。报告统一采样设置下的成绩，也可给各自开发集调优后的最佳成绩，避免用不合适参数压低某模型。

跨 tokenizer 的 token 数不是相同文字量。**速度实验按各自 tokenizer 精确控制 token 长度；对话质量实验使用相同中文语义输入**，两种结果分开报告。

比较算法时同时报告样本/processed tokens、rollout tokens、教师开销和 GPU 小时。只给 GRPO 多十倍数据后宣称算法更好，没有足够解释力。

### 9.3 板端验收必须延续现有口径

现有项目关注全深度语言链路，仍应测历史 512/1024 × 新增 32/64/128 tokens；首字按同一计时边界，保持 KV cache 有效，固定生成长度测性能，另测自然 EOS 聊天体验。

记录 TTFT P50/P95、decode tok/s、完整回复耗时、CPU 利用率、峰值 RSS/内存、swap/I/O、温度、异常；低/中温分组。冷启动、窗口溢出压缩、模型切换单列，不能混进普通增量对话平均值。

这些新增长度是性能矩阵，不代表每个日常用户都会说 128 tokens。另报告实景短句下的“开始出声时间、说完一句所需时间”；语音系统还要加上 ASR/TTS 延迟。

部署链路：原始可训练权重 → LoRA/微调 → 需要时合并 → 导出 → 量化校准/编译 → 全层数值与生成回归 → 板端对话与性能验收。**GGUF、NBG 是部署产物，不作为常规训练起点。** CPU/NPU 同量化程度比较与训练质量比较分开；不能假定微调后 Q8 或 Q4 仍保持之前误差。

## 10. 可行性、执行顺序与停止条件

| 项目 | 可行性判断 | 验证/停止条件 |
| --- | --- | --- |
| 用 SFT 学短句与风格 | 高 | 小样本就应出现可观察改善；没有改善先查数据、模板、loss mask |
| 稳定简单角色设定 | 较高 | 先固定少量设定，扩大轮数；复杂世界观不作为首目标 |
| 商用 API 迭代改写/偏好蒸馏 | 高 | 教师与人工一致，改写不添加事实；收益需独立测试 |
| GRPO 改善自然聊天 | 有条件 | 组内奖励可区分且人工偏好随之改善；否则不扩量 |
| 纯文本 API 完整分布 OPD | 通常受接口限制 | 明确能否评分学生前缀上的指定 token/分布；拿不到就换文本反馈路线 |
| 500M 达到大模型全面聊天能力 | 不应承诺 | 目标收窄到高频日常；识别容量瓶颈，不无限追加数据 |
| 1B 级做实用短聊陪伴 | 值得验证 | 中文底座、数据与角色复杂度共同决定；性能预算同时通过 |
| 微调实现无限长期记忆 | 不可这样期待 | 外部记忆与检索是必要系统设计 |
| 训练后直接复用旧 NPU 二进制 | 不可 | 权重更新后重新导出、校准、编译和回归 |

建议工作包顺序：

1. **定义与抽样（人工为主）**：确定风格，审阅数据源，编写开发集/隔离测试集，教师小型盲测。
2. **最小训练闭环**：两个学生、3k–5k 窗口 SFT；标定显存与吞吐，验证生成和导出。
3. **正式 SFT**：约 30k 窗口；比较配比、长度、人设与记忆分项，避免大范围超参扫网。
4. **学生错误驱动迭代**：商业教师纠错、DPO 与迭代 SFT 对照；逐轮看收益/成本。
5. **条件性 GRPO**：奖励先验收，再试训练；不给它默认更高预算。
6. **最终部署评测**：量化后人工盲评、长短历史速度、真实多轮和稳定性。

上述是待执行方案。本次报告没有购买 API、申请 GPU、训练模型或启动板端任务。

## 11. 后续视觉压缩与 MTP：与聊天训练分开立项

减少 vision tokens 可通过池化、投影/重采样、选择/合并 token 或减少切图等方式，但质量和部署收益要实测。现有 VLM 通常已经包含空间下采样，不能把进一步压缩宣称为“第一次压缩”。对细节/OCR/小目标尤其要单独评测。

同一模型的未压缩版本可以作为压缩分支教师；若目标是修复原模型中文聊天弱点，单靠自蒸馏未必获得缺失能力。视觉压缩主要降低视觉前缀及相关计算，静态 NPU 图若仍按最大窗口计算，减少有效 token 不必然等比例加速。

MTP 是另一类架构/训练与推理工程：增加多 token 预测头通常需要训练，并适配验证/接受机制；也可研究独立 draft 模型的 speculative decoding，但在小模型和静态 NPU 图上收益不保证。**SFT 或 GRPO 本身不会自动让模型获得 MTP 推理能力。** 本阶段先保持架构，降低部署变量。
